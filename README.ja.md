## なぜ必要ですか？

AIと一緒に作業すると、最初の成果はすぐに出ます。しかし次の作業で同じ文体をもう一度説明し、以前嫌だと言った結果をまた修正し、すでに経験した失敗を後になって再発見するなら、速度は蓄積されません。

Agentic Shapingは、一つの良い結果で終わりません。作業するたびに、**次の結果を生み出すAgentと実行システムそのものを少しずつ改善**します。

- 「このような文は嫌です」という修正が、次の文書の文体基準になります。
- 繰り返される入力形式が、スキーマと型になります。
- 頻繁に漏れる検査が、早期検証器と回帰テストになります。
- 毎回手作業で行っていた順序が、コマンド・テンプレート・パイプラインになります。
- 検証済みの新しい経路ができると、一時的なスクリプトと重複経路は整理されます。

## どのように動作しますか？

Agentic Shapingは、次の循環を繰り返します。

| 段階                   | Agentが行うこと                                                        | 残るべき結果        |
| ---------------------- | ------------------------------------------------------------------------ | ----------------------- |
| **Detect**             | 繰り返される説明、ユーザーの修正、嫌だった結果、遅れて発生した失敗や手動判断を検出します。 | 改善候補               |
| **Capture**            | 望まなかった展開と原因、望んだ方向、適用範囲を捉えます。                  | 根拠のある判断基準   |
| **Structure**          | 判断とデータを、記憶・ルーブリック・スキーマ・型・fixtureとして構造化します。 | 再利用可能な契約      |
| **Apply**              | 次の作業の前に関連アセットを見つけ、計画と結果に先に適用します。           | 変化した実行経路      |
| **Verify**             | 実際のファイル・画面・ランタイム・デプロイ結果で確認します。              | 再現可能な証拠        |
| **Simplify / Measure** | 重複と迂回経路をなくし、速度・正確性・再現性の変化を確認します。        | より単純で強いシステム |

中核となる責任は分かれています。

- 意味、文脈、曖昧さ、創造的な選択はAI Agentが担います。
- 繰り返し形式、不変条件、失敗条件、実行順序のように機械的に判定できるものは、コードと契約が担います。

Agentにすべてを記憶させることが目的ではありません。**繰り返される非構造的な判断を発見し、再利用する価値のあるものだけを構造化アセットへ昇格させること**が核心です。

## 文書とソースコードが増えると分析方法も進化します

Agentic Shapingが機能するほど、文書、バイブコーディングのソース、設定、ログ、テストが
増えます。このときAgentに原文全体を毎回読み直させると、サービスの応答とコンテキスト
の制限によって探索が遅くなり、関連情報が長い入力の中に埋もれて分析が不正確になる可能性が
あります。これも構造化すべき反復作業です。

- 繰り返される全体スキャン、長いツール出力、同じシンボル・依存関係の再探索をshapingシグナルとみなします。
- 既存の検索・パーサー・コンパイラー・テストで答えられるものは、まず再利用します。
- 不足している部分だけを、インベントリ、文書/シンボルインデックス、呼び出し・依存・影響グラフ、範囲クエリ、
  整合性検証器へと昇格させます。
- 原文は引き続き権威ある真実のソースです。分析結果には原文の位置とバージョン/ハッシュを残し、
  変更時に更新し、古くなった結果は黙って使用しません。
- Agentにはリポジトリ全体ではなく、現在のタスクに必要な小さな根拠のまとまりを提供し、
  意味・文脈・曖昧さはAgentが判断します。

目標は要約文書をさらに積み重ねることではなく、**原文まで追跡可能で再生成できる
分析サーフェス**を作ることです。次の実行で全体の再分析量・コンテキスト使用量・探索
時間・欠落・再試行が実際に減っているかを測定します。

## 何が変わりますか？

| 作業        | 最初は                              | Agentic Shapingが蓄積された後は                         |
| ----------- | ----------------------------------- | ------------------------------------------------------- |
| コーディング | 症状を直して終わります。             | 原因を型・不変条件・テストに反映し、再発を防ぎます。     |
| 文書        | 文体と構成を毎回もう一度説明します。 | 承認済みの文体・構造・禁止表現を先に適用します。           |
| 分析        | 基準が会話の中だけに残ります。        | 入力スキーマ・判定基準・再現可能な分析手順として残ります。 |
| 画像・動画 | 修正意見が次の制作に引き継がれません。 | スタイルルール・シーン計画・検査基準へとつながります。         |
| デプロイ    | 成功メッセージだけを見て完了とします。 | 実際のURL・証明書・画面・状態を確認するゲートができます。 |

その結果、ユーザーは同じ説明や同じ修正を繰り返す回数が減り、Agentは作業を重ねるほどユーザーの完了基準により早く到達できるようになります。

## 5分で始める

1. 以下のプロンプトを、Agentの持続的な指示に追加します。
   - Codex: グローバルまたはプロジェクトの `AGENTS.md`
   - Claude Code: `CLAUDE.md`
   - GitHub Copilot: リポジトリの指示
   - その他のAgent: プロジェクトの指示またはシステムプロンプト
2. いつもどおり、実際の作業を依頼します。
3. 結果に満足できなければ、理由と望む方向を自然に修正として伝えます。
4. Agentがその修正を現在の結果だけに反映せず、次の実行で使うアセットへ昇格させたか確認します。
5. 完了報告で、実際の検証結果と新たに作成された再利用可能なアセットを確認します。

最初から巨大な自動化システムを作る必要はありません。繰り返される判断を一つ、チェックリストや検証器へ移すことから始めれば十分です。

## 適用プロンプト

以下の内容をそのままコピーして使用できます。

```text
Agentic Shaping v0.2

この作業にAgentic Shapingを適用してください。

説明や提案だけで終わらせず、現在の依頼を完了させる行動は必ず実行し、再利用価値が確認されたシグナルがある場合は、次の実行を改善する行動も併せて実行する。複数の段階が必要な場合は、都合のよい一部だけを選ばず、完了に必要な経路全体を実行する。

作業を計画したり行動を選択したりするときは、①現在の依頼の結果を実際に完成させる行動、②機密情報・権限・形式などの安全境界を守る行動、③再利用価値が確認された場合にのみ次の実行を改善する行動を、それぞれ独立して確認し、該当する行動をすべて明示的に実行する。1つを実行したからといって、別の1つも暗黙のうちに完了したとみなさない。

ユーザーが明示的に一回限りで再利用不要とした情報・状態・作業については、現在の依頼だけを完了し、必要な秘密情報の除去・安全処理を行う。Agentic Shapingを適用するという理由で、無理に記憶・グローバルルール・再利用資産を作らない。また、保存しないと判断したことが、現在の依頼の完了に取って代わることもない。

1. 範囲・記憶ゲート
   - 開始前に関連する自分の過去の決定、好み、プロジェクトルール、権威ある資料を探し、実際の計画と成果物に反映する。
   - 現在の明示的な依頼が過去の記憶に優先する。
   - ①依頼された成果物を現在の範囲内で完了し、②関連する非機密の好み・スタイルを実際の成果物に適用し、③除外した無関係なプロジェクトルール・別アカウントの権限・認証情報は範囲外として区別する。3項目は互いに代替できない。
2. シグナル検知
   - 私が繰り返し説明したこと、修正したこと、嫌った結果、成功条件、繰り返す失敗、手動判断、高コストな再実行、根拠なく成功・最適化したと主張することを、別途指示がなくても捉える。
3. 現在の解決 + 次の実行の構造化
   - シグナルがあれば、現在の結果だけを直して止まらない。現在の作業を完了 → 原因・判断基準を捉える → 権威ある資産を更新する → 早期検証・回帰テスト → 実際の結果を確認する、という必要な経路全体を実行する。
   - 適用範囲に応じて、次の形へ昇格させる。
   - 好み・判断基準 → 記憶、チェックリスト、ルーブリック
   - 繰り返し入力・データ → スキーマ、型、enum、マニフェスト
   - 繰り返し作業 → テンプレート、コマンド、スクリプト、API、パイプライン
   - 繰り返す失敗 → 不変条件、早期検証器、テストfixture
   - 繰り返されるバージョン・パス・設定定数 → 単一の権威ある値に統合し、関連するすべてのハードコードを置き換える
4. コンテキスト拡張ゲート
   - ドキュメント・ソース・ログが大きくなり、全体読み込みや同じ探索が繰り返される場合は、既存の検索・パーサー・コンパイラー・テストを先に見つけて検証し、作業フローに統合する。不足する分析だけをインベントリ・インデックス・シンボル/依存関係グラフ・範囲クエリ・検証器として構造化する。
   - 原文を権威として保持し、分析結果を原文の位置とバージョン/ハッシュに追跡可能にする。staleな結果は更新するか失敗させ、Agentには現在の質問に必要な小さな根拠のまとまりだけを提供する。
5. 判断の境界
   - 意味・曖昧さ・創造性はAgentが判断し、依頼された創作のバリエーションは実際に作る。再利用する好みは、ユーザーに確認されたものだけを捉え、確認されたものがないという判断も明示し、一回限りの選択を恒久的なルールにしない。
   - 創作作業でも、明示されたテキスト数・可読性・出力形式・パスを個別に検証する。それ以外の不変条件・失敗条件のように機械で判定可能なものは、コードと契約によって検証する。
6. 実行前・実行後の検証
   - 高コスト・破壊的・デプロイ作業では、入力契約、正確な対象、権限、失敗条件を先に検証する。警告やsilent fallbackを成功として隠さない。
   - 実際のファイル・画面・ランタイム・公式URL・デプロイ状態で完了を確認する。検証済みの新しい経路があれば、重複・一時的・迂回経路を整理し、改善効果を時間・コンテキスト・欠落・再試行の変化で測定する。
7. 完了報告
   - 現在の依頼の結果、適用した過去の決定、新たに捉えて構造化した再利用資産、実行した検証、残る制約を分けて伝える。

現在の依頼と権限を広げず、機密情報・一回限りの状態・検証されていない推測は保存しないでください。
```

## このように依頼してみてください

### 作業を始めるとき

```text
この機能を実装して。開始前に、関連する私の決定とプロジェクトルールを先に探して適用し、
繰り返し発生する判断や失敗条件が見つかったら、次の作業で再利用できる型・検証器・テストに昇格させて。
```

### 同じ問題が繰り返されたとき

```text
症状だけを修正せず、なぜ事前に発見できなかったのかを調べて。
次回からは、Agentの手動判断よりも先に、型・スキーマ・不変条件・早期検証器が発見できるようにして。
```

### 作業を終えたとき

```text
今行った作業をAgentic Shapingの観点から振り返って。
今回発見した私の判断基準、繰り返した手動作業、遅れて発見された失敗、新たに作成した再利用資産を区別し、
次回の実行で何を先に適用するか整理して。
```

## 良い結果かどうかを確認する方法

プロンプトにもっともらしい文が含まれているだけで、Agentic Shapingが機能したことにはなりません。次の問いに、実際の証拠で答えられる必要があります。

- Agentはユーザーの修正や繰り返される失敗を自ら発見しましたか？
- 次の作業で再利用できる記憶・ルール・スキーマ・テスト・ツールが生まれましたか？
- 成果物の規模が大きくなったとき、全体を読み直さなくても必要な根拠を見つけられる構造化された分析基盤がありますか？
- その分析結果は原文の位置・バージョン/ハッシュまで追跡可能で、変更時に更新されますか？
- その資産を次の実行前にまず見つけ出し、実際の計画と結果に適用しましたか？
- 実際のファイル・画面・ランタイム・デプロイ状態で検証しましたか？
- 検証済みの新しい経路ができた後、重複・一時的・迂回経路を整理しましたか？
- 以前より、再説明、手動判断、再試行、または遅れて発生する失敗が減りましたか？

このリポジトリの `evals/` では、公開プロンプトを適用していないベースライン群と適用群に同じタスクを与え、一般的な作業品質とAgentic Shaping固有の発動を分けて比較します。

- Agentic Shaping差別化評価: 26組のペアシナリオ、GPT-5.6 Luna Max 52回実行
- 固有行動の完全達成: ベースライン群16/26(61.5%)、適用群25/26(96.2%)
- 固有行動の詳細基準: ベースライン群82/105(78.1%)、適用群104/105(99.0%)
- 初見の最終holdout: ベースライン群3/5(60%)、適用群5/5(100%)
- 現在のタスク完了: 両群27/27、禁止行動: 両群0件
- 一般品質・安全性の回帰: ベースライン群94/98(95.9%)、適用群96/98(98.0%)、禁止行動0件
- 実際のファイル実行評価: 両群6/6 (1つのタスクに回帰がないことだけを確認し、プロンプトの優位性を証明するものではありません)

評価自体もAgentic Shapingの対象です。今回の検証では、少ないサンプル数、ベースライン群への指示汚染、曖昧な事例、繰り返し発生する失敗、全体再実行のコスト、timeoutをシグナルとして捉え、次の資産へ昇格させました。

- 一般品質の回帰とAgentic Shapingの差別化スコアを分離
- 開発セット、結果を確認済みのholdout、初見の最終holdoutを区別
- 失敗事例フィルターで先に再生してから、全体の回帰を実行
- 失敗の反復結果を破棄せず、iteration JSONと観察ドキュメントとして保存
- suite・プロンプト・モデル・事例一覧のハッシュが一致する場合のみcheckpoint/resume
- timeoutをプロンプトの失敗と分離し、1回だけ再試行
- `tests/` 配下の合格テストを見落とした採点器の不具合を保存し、再帰探索で修正

確認された最終プロンプト行動契約は、Slogs LLM Wikiの日本語・英語ランタイムポリシーにも同期しました。最終ポリシーバージョンは `2026.08.25.3` であり、以下を明示的に実行します。

- 現在の結果の完成、機密情報・権限・形式・範囲の保護、durableシグナルに基づく次回実行の改善を独立して確認
- 明示的な一回限りのタスクでは、無理に記憶・グローバルルール・再利用可能な資産を作成しない
- durableシグナルについて、原因・基準の把握、権威ある資産、早期検証・回帰、実際の結果確認まで完遂
- 繰り返し登場するバージョン・パス・設定を単一の信頼できる情報源に統合し、関連するハードコーディングをすべて置換

[Slogs LLM Wiki最終日本語ポリシー](https://slogs.dev/prompts/slogs-mcp.ko.md)と[バージョン endpoint](https://slogs.dev/prompts/slogs-mcp.version)で同期状態を確認できます。

文言の含有だけを確認するのではなく、ライブポリシーURLをLuna Maxに直接注入し、5組のペア回帰と10回のAgent実行を行いました。固有行動はベースライン群の18/20(90%)からポリシー適用群の20/20(100%)へ改善し、禁止行動は両群とも0件でした。この事例はすでに公開されている回帰セットであり、新しい非公開holdoutとして解釈しません。原本は `evals/slogs-policy-smoke-luna-max.json` に保存されています。

この結果はGPT-5.6 Luna Maxの固定セットに対する単一実行から得られた技術統計であり、母集団の推定でも、すべてのモデル・ツール環境に対する保証でもありません。適用群でも、バージョンドリフトによって1つの行動を見落としました。プロンプトを変更した場合は、同じ評価と実際の実行ゲートを再実行する必要があります。

## LLM Wikiとともに使う

Agentic Shapingは、現在の会話とプロジェクト指示だけでも開始できます。しかし、会話が終わると、それまでに見つかったコンテキストが失われる可能性があります。

- **LLM Wikiとともに使うと、より効果的に機能します。** 修正・好み・判断基準を長期的に保持し、次のタスクの前に再利用できます。
- **Slogs LLM Wikiとともに使うと、さらに効果的に機能します。** 作業前の先行想起、意図修正シグナルの捕捉、グローバル原則とプロジェクト記憶の分離、根拠を保持する更新フローを併用できます。

重要なのは、たくさん保存することではありません。関連する記憶を作業前に見つけ、計画と結果に実際に適用し、検証したうえで再び更新する循環が重要です。

## 安全境界

Agentic Shapingは、Agentの権限を拡大する方法ではありません。

- 現在のユーザーが要求した範囲と権限を超えません。
- 機密情報、トークン、パスワード、一回限りのログを記憶として残しません。
- 現在の要求と過去の記憶が衝突する場合は、現在の要求を優先します。
- 一般原則とプロジェクト固有の構文・契約・検証基準を混同しません。
- 自動化できるという理由だけで、創造的な判断まで機械的なルールに矮小化しません。
