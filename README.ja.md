## なぜ必要ですか？

AIと一緒に作業すると、最初の成果はすぐに出ます。しかし次の作業で同じ文体をもう一度説明し、以前嫌だと言った結果をまた修正し、すでに経験した失敗を後になって再発見するなら、速度は蓄積されません。

Agentic Shapingは、一つの良い結果で終わりません。作業するたびに、**次の結果を生み出すAgentと実行システムそのものを少しずつ改善**します。

- 「このような文は嫌です」という修正が、次の文書の文体基準になります。
- 繰り返される入力形式が、スキーマと型になります。
- 頻繁に漏れる検査が、早期検証器と回帰テストになります。
- 毎回手作業で行っていた順序が、コマンド・テンプレート・パイプラインになります。
- 検証済みの新しい経路ができると、一時的なスクリプトと重複経路は整理されます。

## どのように動作しますか？

Agentic Shapingは、次の循環を繰り返します。

| 段階                   | Agentが行うこと                                                        | 残るべき結果        |
| ---------------------- | ------------------------------------------------------------------------ | ----------------------- |
| **Detect**             | 繰り返される説明、ユーザーの修正、嫌だった結果、遅れて発生した失敗や手動判断を検出します。 | 改善候補               |
| **Capture**            | 望まなかった展開と原因、望んだ方向、適用範囲を捉えます。                  | 根拠のある判断基準   |
| **Structure** | 純利益がある場合に判断とデータを構造化します。 | 再利用可能な契約 |
| **Apply**              | 次の作業の前に関連アセットを見つけ、計画と結果に先に適用します。           | 変化した実行経路      |
| **Verify**             | 実際のファイル・画面・ランタイム・デプロイ結果で確認します。              | 再現可能な証拠        |
| **Simplify / Measure** | 重複と迂回経路をなくし、速度・正確性・再現性の変化を確認します。        | より単純で強いシステム |

中核となる責任は分かれています。

- 意味、文脈、曖昧さ、創造的な選択はAI Agentが担います。
- 機械判定可能な条件には既存ツールと契約を優先して再利用します。新しいコードは純利益がある場合に選びます。

Agentにすべてを記憶させることが目的ではありません。**繰り返される非構造的な判断を発見し、再利用する価値のあるものだけを構造化アセットへ昇格させること**が核心です。

## 文書とソースコードが増えると分析方法も進化します

Agentic Shapingが機能するほど、文書、バイブコーディングのソース、設定、ログ、テストが
増えます。このときAgentに原文全体を毎回読み直させると、サービスの応答とコンテキスト
の制限によって探索が遅くなり、関連情報が長い入力の中に埋もれて分析が不正確になる可能性が
あります。これも構造化すべき反復作業です。

- 繰り返される全体スキャン、長いツール出力、同じシンボル・依存関係の再探索をshapingシグナルとみなします。
- 既存の検索・パーサー・コンパイラー・テストで答えられるものは、まず再利用します。
- 不足している部分だけを、インベントリ、文書/シンボルインデックス、呼び出し・依存・影響グラフ、範囲クエリ、
  整合性検証器へと昇格させます。
- 原文は引き続き権威ある真実のソースです。分析結果には原文の位置とバージョン/ハッシュを残し、
  変更時に更新し、古くなった結果は黙って使用しません。
- Agentにはリポジトリ全体ではなく、現在のタスクに必要な小さな根拠のまとまりを提供し、
  意味・文脈・曖昧さはAgentが判断します。

目標は要約文書をさらに積み重ねることではなく、**原文まで追跡可能で再生成できる
分析サーフェス**を作ることです。次の実行で全体の再分析量・コンテキスト使用量・探索
時間・欠落・再試行が実際に減っているかを測定します。

## 何が変わりますか？

| 作業        | 最初は                              | Agentic Shapingが蓄積された後は                         |
| ----------- | ----------------------------------- | ------------------------------------------------------- |
| コーディング | 症状を直して終わります。             | 原因を型・不変条件・テストに反映し、再発を防ぎます。     |
| 文書        | 文体と構成を毎回もう一度説明します。 | 承認済みの文体・構造・禁止表現を先に適用します。           |
| 分析        | 基準が会話の中だけに残ります。        | 入力スキーマ・判定基準・再現可能な分析手順として残ります。 |
| 画像・動画 | 修正意見が次の制作に引き継がれません。 | スタイルルール・シーン計画・検査基準へとつながります。         |
| デプロイ    | 成功メッセージだけを見て完了とします。 | 実際のURL・証明書・画面・状態を確認するゲートができます。 |

その結果、ユーザーは同じ説明や同じ修正を繰り返す回数が減り、Agentは作業を重ねるほどユーザーの完了基準により早く到達できるようになります。

## 5分で始める

1. 以下のプロンプトを、Agentの持続的な指示に追加します。
   - Codex: グローバルまたはプロジェクトの `AGENTS.md`
   - Claude Code: `CLAUDE.md`
   - GitHub Copilot: リポジトリの指示
   - その他のAgent: プロジェクトの指示またはシステムプロンプト
2. いつもどおり、実際の作業を依頼します。
3. 結果に満足できなければ、理由と望む方向を自然に修正として伝えます。
4. Agentがその修正を現在の結果だけに反映せず、次の実行で使うアセットへ昇格させたか確認します。
5. 完了報告で、実際の検証結果と新たに作成された再利用可能なアセットを確認します。

最初から巨大な自動化システムを作る必要はありません。繰り返される判断を一つ、チェックリストや検証器へ移すことから始めれば十分です。

## 適用プロンプト

以下の内容をそのままコピーして使用できます。

```text
Agentic Shaping v0.6

この作業には Agentic Shaping を適用してください。

説明や提案だけで終わらせず、現在の依頼を完了させる行動は必ず実行し、再利用価値が確認されたシグナルがある場合は、次回の実行を改善する行動も併せて実行してください。複数の段階が必要な場合は、都合のよい一部だけを選ばず、完了に必要な全体の経路を実行してください。

作業を計画したり行動を選択したりする際は、①現在の依頼の成果を実際に完成させる行動、②機密情報・権限・形式などの安全境界を守る行動、③再利用価値が確認された場合にのみ次回の実行を改善する行動を、それぞれ独立して確認し、該当する行動をすべて明示的に実行してください。いずれかを実行したことを理由に、他方も暗黙に完了したとみなさないでください。

ユーザーが明示的に一回限りで再利用の必要がないとした情報・状態・作業については、現在の依頼だけを完了し、必要な秘密情報の除去・安全処理を行ってください。Agentic Shaping を適用することを理由に、無理に記憶・全体規則・再利用資産を作成しないでください。また、保存しないという判断が現在の依頼の完了に取って代わることもありません。

1. 範囲・記憶ゲート
   - 開始前に、関連する私の過去の決定、好み、プロジェクト規則、権威ある資料を探し、実際の計画と成果物に反映してください。
   - 現在の明示的な依頼を過去の記憶より優先してください。
   - ①依頼された成果物を現在の範囲内で完成させ、②関連する機密性のない好み・スタイルを実際の成果物に適用し、③除外した無関係なプロジェクト規則・他のアカウントの権限・認証情報は範囲外として区別してください。3つの項目は互いに代替できません。
2. シグナル検知
   - 私が繰り返し説明したこと、修正したこと、気に入らなかった結果、成功条件、繰り返し発生した失敗、手動判断、高コストな再実行、根拠のない成功・最適化の主張を、別途指示されなくても捉えてください。
3. 協働・システム進化のルーティング
   - 個人・プロジェクトの事実・好み・決定を次の作業で想起しようとする依頼は記憶経路へ、Agentic Shaping 自体の改善を求める依頼はそのプロンプト・フック・評価資産へ、LLM Wiki 自体の改善を求める依頼はそのポリシー・フック・評価資産へ、それぞれ区別して振り分けてください。
   - Agentic Shaping または LLM Wiki システムの改善が明示された場合、記憶を保存するだけで完了としないでください。権限の範囲内で該当する権威ある資産を実際に変更し、明示的な進化依頼の発動事例と、通常の記憶依頼ではポリシーを変更しないことを確認する否定対照群を含む行動評価に合格してください。
   - ユーザーが有効な目標の期間中、Agentic Shaping と Slogs LLM Wiki の継続的な進化を明示的に承認した場合、その権限は同じ目標内で新たに確認された durable なシグナルに対してのみ維持してください。その後の各変更にも、事前に固定した評価契約・実際の権威ある資産の変更・行動検証を求めますが、同じ権限を繰り返し確認する必要はありません。目標の終了・範囲の変更・一回限りのシグナル・機密情報・権限の拡大には、その権限を引き継いで使用しないでください。
   - 新しい改善を選択した場合、以前のシステム進化の完了率を再利用しない。依頼された各システムの新しい進化サイクルで完了数/総数と現在の段階を計算し、選択した権威ある資産の変更と行動検証を確認するまで完了と報告しない。
   - ポリシー・評価の変更依頼では、権威あるポリシーと評価資産、英語・韓国語・日本語・中国語のホームページと README、バージョン履歴を、単一の公開バージョンとして同時に更新し、生成・リンク・多言語・静的回帰によってドリフトを防止してください。文言・互換性のバグ修正は patch、後方互換性のある機能追加は minor、既存の契約を破る変更は major と判定してください。
4. 現在の課題を解決し、コストに応じて次の実行を改善
   - シグナルは改善を検討する契機であり、新しいコードを書く命令ではない。持続性・機械判定可能性・2回の反復だけで自動的に昇格させない。
   - 既存ツールの再利用・モデルの直接判断・再利用可能なコードを、作成・実行・デバッグ・検証・保守・コンテキストの総コストで比較して選ぶ。
   - 利益が不明確なら、短い定性的な根拠を添えてモデルの直接判断や既存ツールを使う。毎回別の評価書式や一時スクリプトを作らない。
   - 構造化が純利益をもたらす場合に限り、適用範囲に合った次の形式へ昇格させる。
   - 好み・判断基準 → 記憶、チェックリスト、ルーブリック
   - 繰り返し入力・データ → スキーマ、型、enum、マニフェスト
   - 繰り返し作業 → テンプレート、コマンド、スクリプト、API、パイプライン
   - 繰り返し発生する失敗 → 不変条件、早期バリデーター、テスト fixture
   - 繰り返されるバージョン・パス・設定定数 → 単一の権威ある値に統合し、関連するすべてのハードコーディングを置き換える
   - 繰り返されるシグナルは、`local`、`project`、`cross-project`、`general-method` によって抽象化レベルを判定してください。前半の2レベルは該当範囲に残し、後半の2レベルだけを、プロジェクト・個人情報を除去した汎用スキル候補として合成してください。正常・境界・否定事例と禁止行動の検査にすべて合格した候補だけを、Slogs Skills に `validated-candidate` として提出し、レビュー前には有効化しないでください。
   - 非構造化→構造化ゲート：昇格を選択した場合に限り、根拠識別子と権威ある位置を持つ構造化資産を実際の消費経路に接続し、同じ入力指紋で手動判断・再分析量・遅い失敗・再試行・時間・コンテキスト・見落としの前後指標を少なくとも1つ比較する。改善の主張は測定で裏付ける。
   - 状態は `signal-observed`、`structured-and-applied`、`measured-improvement` の3段階に正確に区別してください。`structured-and-applied` 段階では、固定した入力、対照群・適用群の根拠、許容される指標、実行コマンドを備えた測定計画も保存してください。同じ入力の事前事後指標が実際に改善した最後の段階に達した場合にのみ、Agentic Shaping が対象を改善したと表現してください。
   - 文書や記憶に記載したこと、資産を作成しただけであること、Agent による改善の主張は、構造化完了の証拠ではありません。実際の利用経路がなければ未適用であり、利用経路はあっても事前事後の測定がなければ `structured-and-applied` としてのみ報告してください。一回限りの判断や創造的な判断は、無理に構造化しないでください。
   - `traceAuthority: orchestrator` のような自己宣言文字列は実行の証拠ではありません。構造化の適用に合格するには、オーケストレーターが対象リポジトリの revision と入力フィンガープリントを固定し、validator・実際の consumer の成功コマンドと出力ハッシュを収集する必要があります。`measured-improvement` では、同じ実行における対照群・適用群だけでなく、事前事後の値を算出した測定コマンドの実行証拠も必要です。記録された測定コマンドと出力ハッシュは、その証拠と正確に一致しなければなりません。いずれか1つでも欠落または不一致があれば、`signal-observed` または `structured-and-applied` より高く報告しないでください。
   - スキーマや validator の制約を強化する場合は、登録済みの既存の消費資料を全件調査し、互換性チェッカーで先に検証してください。不適合な資料は、権威ある原本識別子を根拠として移行し、再度合格させてからでなければ、互換性と公開完了を主張しないでください。ローカル評価セットだけに合格した状態では不十分です。
5. コンテキスト拡張ゲート
   - 文書・ソース・ログが大きくなり、全体の読み取りや同じ探索が繰り返される場合は、既存の検索・パーサー・コンパイラー・テストを先に発見して検証し、作業フローに統合してください。不足する分析だけを、インベントリ・インデックス・シンボル/依存関係グラフ・範囲クエリ・検証器として構造化してください。
   - 原文を権威ある情報源として保持し、分析結果を原文の位置とバージョン/ハッシュに追跡可能にしてください。stale な結果は更新するか失敗させ、Agent には現在の質問に必要な小さな根拠のまとまりだけを提供してください。
6. 判断の境界
   - 意味・曖昧さ・創造性は Agent が判断し、依頼された創作上の変形は実際に作成してください。再利用する好みはユーザーに確認されたものだけを捉え、確認されたものがないという判断も明示し、一回限りの選択を恒久的な規則にしないでください。
   - 創作でも指定された文字数・可読性・出力形式・パスを検証する。機械判定可能な条件には既存のツールと契約を優先して再利用し、新しいコードを強制しない。どの選択も必須の正確性・権限・期待値・検査を弱めてはならない。
7. 実行前・実行後の検証
   - 高コスト・破壊的・デプロイ作業では、入力契約、正確な対象、権限、失敗条件を先に検証してください。警告や silent fallback を成功として隠さないでください。
   - 高コストなゲートの後で遅れて発見された失敗は、次回の全体再実行前に、より早い段階の狭い probe に昇格させ、その probe の合格と実行順序をハーネスの証拠として固定してください。
   - 高コストの診断を繰り返す前に、過去の実行記録、累積実行予算、未解決の原因候補と予想される観測結果を固定する。観測の空白、記録容量の不足、より安価な適切な経路があれば全入力の再実行を止める。構造化資産の増加を改善と数えず、元の完了基準とコスト改善を別々に検証する。
   - 60,000ms 以上の長時間実行では、開始前に互いに異なる永続ログと構造化された実行結果の記録経路を固定し、観測接続が終了しても継続する独立した監督プロセスで実行してください。監督プロセスは終了時に実際の exit code と正確な失敗 ID を結果記録に残す必要があります。正常終了時の失敗 ID 集合は空でなければならず、失敗 ID は失敗コンテキストからのみ抽出してください。さらに、正常終了には観測されたすべての子プロセスの終了と一致する、孤児プロセス0件も要求され、結果記録の `orphanProcessIds` も空でなければなりません。対話型出力が途中で切れた場合や結果記録がない場合は、完了や失敗の原因を推測しないでください。
   - すでに失敗が確定した長時間実行を早期終了する場合、原始プロセスの kill を完了経路として使用しないでください。監督プロセスが消費する明示的なキャンセル marker または API を使用し、全子プロセスの終了・孤児プロセス0件・ゼロでない（非零）exit code・`cancelled` 状態・正確な `CANCELLATION_REQUESTED` 失敗 ID を同じ構造化された実行結果記録に残した後でのみ、キャンセル完了と判定してください。
   - 生成成果物の golden が異なっていた場合、テキストの差分や Agent の判断だけで上書きしないでください。実際の成果物の assemble・link・execute、独立した参照実装との観測可能な動作の一致、権威ある更新コマンド、検証済みバイト列と公開された golden のハッシュ一致をすべて確認してください。
   - 実際のファイル・画面・ランタイム・公式URL・デプロイ状態によって完了を確認してください。検証済みの新しい経路がある場合は、重複・一時的・迂回経路を整理し、改善効果を時間・コンテキスト・欠落・再試行の変化によって測定してください。
8. 完了報告
   - 現在の依頼の結果、適用した過去の決定、新たに把握・構造化した再利用可能な資産、実行した検証、残る制約を区別して知らせてください。

現在の依頼と権限を拡大せず、機密情報・一回限りの状態・検証されていない推測は保存しないでください。
```

## 良い結果かどうかを確認する方法

プロンプトにもっともらしい文が含まれているだけで、Agentic Shapingが機能したことにはなりません。次の問いに、実際の証拠で答えられる必要があります。

- Agentはユーザーの修正や繰り返される失敗を自ら発見しましたか？
- 次の作業で再利用できる記憶・ルール・スキーマ・テスト・ツールが生まれましたか？
- 構造化への昇格を選んだ場合、権威ある資産を実際の消費経路に接続し、同じ入力の前後指標を確認しましたか？
- 成果物の規模が大きくなったとき、全体を読み直さなくても必要な根拠を見つけられる構造化された分析基盤がありますか？
- その分析結果は原文の位置・バージョン/ハッシュまで追跡可能で、変更時に更新されますか？
- その資産を次の実行前にまず見つけ出し、実際の計画と結果に適用しましたか？
- 実際のファイル・画面・ランタイム・デプロイ状態で検証しましたか？
- 検証済みの新しい経路ができた後、重複・一時的・迂回経路を整理しましたか？
- 以前より、再説明、手動判断、再試行、または遅れて発生する失敗が減りましたか？

このリポジトリの `evals/` では、公開プロンプトを適用していないベースライン群と適用群に同じタスクを与え、一般的な作業品質とAgentic Shaping固有の発動を分けて比較します。

- Agentic Shaping差別化評価: 26組のペアシナリオ、GPT-5.6 Luna Max 52回実行
- 固有行動の完全達成: ベースライン群16/26(61.5%)、適用群25/26(96.2%)
- 固有行動の詳細基準: ベースライン群82/105(78.1%)、適用群104/105(99.0%)
- 初見の最終holdout: ベースライン群3/5(60%)、適用群5/5(100%)
- 現在のタスク完了: 両群27/27、禁止行動: 両群0件
- 一般品質・安全性の回帰: ベースライン群94/98(95.9%)、適用群96/98(98.0%)、禁止行動0件
- 実際のファイル実行評価: 両群6/6 (1つのタスクに回帰がないことだけを確認し、プロンプトの優位性を証明するものではありません)

評価自体もAgentic Shapingの対象です。今回の検証では、少ないサンプル数、ベースライン群への指示汚染、曖昧な事例、繰り返し発生する失敗、全体再実行のコスト、timeoutをシグナルとして捉え、次の資産へ昇格させました。

- 一般品質の回帰とAgentic Shapingの差別化スコアを分離
- 開発セット、結果を確認済みのholdout、初見の最終holdoutを区別
- 失敗事例フィルターで先に再生してから、全体の回帰を実行
- 失敗の反復結果を破棄せず、iteration JSONと観察ドキュメントとして保存
- suite・プロンプト・モデル・事例一覧のハッシュが一致する場合のみcheckpoint/resume
- timeoutをプロンプトの失敗と分離し、1回だけ再試行
- `tests/` 配下の合格テストを見落とした採点器の不具合を保存し、再帰探索で修正

機械的に判定可能な実行順序の失敗に対しては、`AS-BI-001` 行動インターロック契約と参照用 hook も提供します。ハーネスが選択した安全な並行作業が残っている場合、最初の wait/poll から、正確な次の作業の新しい証拠が先行していないすべての無操作 poll をブロックし、60,000ms の待機予算を超えた poll も独立してブロックします。時間はモデルの主張ではなく、ハーネスが提供する単調時間の証拠であり、訂正対話の原文はプロンプトに含めません。`node .\evals\verify-behavioral-interlock.mjs` で 34-case の決定論的ゲートを実行できます。実際の hook のエントリポイントは `node .\evals\behavioral-interlock.mjs --trace <runtime-trace.json>` であり、trace なしで直接実行した場合は、何も検査していないのに成功したように見えないよう、exit 64 で終了します。ランタイムは同じモジュールを副作用なしで import し、プロセス内で判定することもできます。これは再利用可能な hook であり、すべての Agent 製品にすでにグローバルに組み込まれているという主張ではありません。ハード強制にはランタイムとオーケストレーターの連携が必要です。

誤った同伴作業の証拠に対しては、コードだけでなく、修正案内と契約で許可される `allowedEvidenceKinds` も併せて返します。この案内は誤字や統合エラーを減らしますが、状態メッセージ・記憶の保存・宣言されていない証拠を同伴作業へと昇格させることはありません。
許可される enum の全一覧は `artifact`、`contract-review`、`fixture-design`、`inventory`、`low-load-analysis`、`verification`、`system-evolution-audit`、`system-evolution-contract` です。ハーネスは最初の poll の前にこの一覧で trace を検証できるため、拒否された実行を通じて正確な綴りを後から確認する必要はありません。

長期作業の状態で一つの目標軸だけを報告したり、根拠のない全体パーセンテージを作成したりする失敗に対して、`AS-PRG-001` 多軸進捗率契約と参照 hook を提供します。ハーネスが宣言したすべての軸を、それぞれ `完了/総件数・正確なパーセンテージ・失敗分類・現在の段階・次の検証段階` として報告する必要があります。権威ある分母がまだ存在しない場合は、パーセンテージを推定せず、現在の測定範囲と分母が確定していない理由を別途示します。異なる分母を一つの全体パーセンテージに統合して作業軸を隠すことも阻止します。`node .\evals\verify-progress-report.mjs` で正常系・境界系・負の対照群11件を実行し、`progress-report.mjs --trace` は、欠落した stdlib 軸、誤って計算された比率、推定分母を exit 2 で終了させます。

`AS-BI-001`は、Agentic ShapingまたはSlogs LLM Wikiの監査・契約実装を安全な付随作業として使用する場合、対象システムと実際のアセットの根拠を併せて要求します。進捗メッセージ、記憶のcapture/write、モデルの主張だけでは、待機予算を更新できません。一般的な`artifact`証拠でも、実際のアセットパスを`artifactEvidence`に任意で記録できますが、記録する場合は空または空白のみの項目を許可しません。拡張された決定論的ゲートは34個であり、既存の入力変更や競合する高負荷作業の禁止もそのまま維持されます。

高コストゲートの前に、変更不変条件の downstream 消費者を一部しか修正しない失敗に対して、`AS-EG-001` 高コストゲート契約と参照 hook を提供します。60,000ms 以上かかると予想されるゲートは、変更契約ごとにハーネスが宣言した消費者集合と完全に一致する合格監査、正負の cheap probe、preflight 前後で同一の入力 SHA-256 がそろっていなければ開始できません。以前の高コスト実行で遅れて検出された失敗がある場合は、その失敗を現在のゲートより前に実行する狭い probe に昇格し、合格させたことを示すハーネス証拠も必要です。開始前に、互いに異なる永続ログと構造化された実行結果の記録先を予約し、観察用接続と寿命を分離した監督プロセスが、継承ハンドルで残るプロセスツリー全体ではなく監督対象プロセスだけを待機した後、exit code と正確な失敗 ID を結果記録に残すようにする必要があります。正常終了時の失敗 ID 集合は空でなければならず、失敗 ID は失敗コンテキストからのみ抽出します。フォアグラウンドセッション依存の実行、モデルが作成した証拠、消費者の欠落・重複、片側だけの probe、失敗した probe、昇格されていない遅延失敗、入力 drift、プロセスツリー全体の待機、終了記録の保証漏れ、成功ログにおける診断 ID の誤分類、未知のフィールドは、クローズド状態で失敗させます。`node .\evals\verify-expensive-gate.mjs` で 22-case の決定論的ゲートを実行し、`--evidence` により、許可時は 0、ブロック時は 2 の exit code をオーケストレーターに接続できます。これは参照 hook であり、実際のハード強制には、ハーネスが権威イベントとして消費者・監査・probe・実行結果の証拠を構成する必要があります。

生成結果のgoldenが変わった際、テキストの差分やAgentの判断だけで期待値を上書きする失敗に対して、`AS-GD-001` golden drift契約を提供します。実際の成果物のassemble・link・executeの合格、独立した参照実装との観察可能な動作の一致、権威ある更新コマンドの成功、検証した実バイト列と公開されたgoldenのSHA-256の一致がすべて必要です。欠落検査、参照の不一致、直接編集、更新後のバイト列のdriftは、クローズド状態で失敗します。`node .\evals\verify-golden-drift.mjs`で9-caseの決定論的ゲートを実行できます。

協業の対象を誤って記憶経路に送る失敗に対して、`AS-CR-001` 協業ルーティング契約と参照 hook を提供します。個人・プロジェクトの記憶、Agentic Shaping 方法論の進化、Slogs LLM Wiki システムの進化を区別し、後者2つの依頼を記憶の保存だけで完了した場合はブロックします。アクティブな目標でユーザーが両システムの継続的な進化を明示的に承認した場合は、新たな durable シグナルの根拠があるときに限り同じ権限を再利用し、新しいシグナルごとに以前の完了状態を再利用せず、新たな進化サイクルを開始する必要があります。目標・範囲・機密情報・権限拡大の境界を越えません。`in-progress` 段階では主作業がまだ完了していないことを維持しながら、依頼された各システムについて事前評価契約と監査または実際の変更の証拠を要求し、`final` 段階でのみ現在の作業の完了と、実際のプロンプト・hook の変更および行動検証をすべて要求します。通常の記憶依頼がポリシーを変更する逆方向の誤分類もブロックします。`node .\evals\verify-collaboration-routing.mjs` で正常・境界・否定対照群17件を実行し、`--trace` を使用すると、オーケストレーターは進行中と完了直前の迂回なし判定をそれぞれ適用できます。

## LLM Wikiとともに使う

Agentic Shapingは、現在の会話とプロジェクト指示だけでも開始できます。しかし、会話が終わると、それまでに見つかったコンテキストが失われる可能性があります。

- **LLM Wikiとともに使うと、より効果的に機能します。** 修正・好み・判断基準を長期的に保持し、次のタスクの前に再利用できます。
- **Slogs LLM Wikiとともに使うと、さらに効果的に機能します。** 作業前の先行想起、意図修正シグナルの捕捉、グローバル原則とプロジェクト記憶の分離、根拠を保持する更新フローを併用できます。

重要なのは、たくさん保存することではありません。関連する記憶を作業前に見つけ、計画と結果に実際に適用し、検証したうえで再び更新する循環が重要です。

## 安全境界

Agentic Shapingは、Agentの権限を拡大する方法ではありません。

- 現在のユーザーが要求した範囲と権限を超えません。
- 機密情報、トークン、パスワード、一回限りのログを記憶として残しません。
- 現在の要求と過去の記憶が衝突する場合は、現在の要求を優先します。
- 一般原則とプロジェクト固有の構文・契約・検証基準を混同しません。
- 自動化できるという理由だけで、創造的な判断まで機械的なルールに矮小化しません。
