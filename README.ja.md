## なぜ必要ですか？

AIと一緒に作業すると、最初の成果はすぐに出ます。しかし次の作業で同じ文体をもう一度説明し、以前嫌だと言った結果をまた修正し、すでに経験した失敗を後になって再発見するなら、速度は蓄積されません。

Agentic Shapingは、一つの良い結果で終わりません。作業するたびに、**次の結果を生み出すAgentと実行システムそのものを少しずつ改善**します。

- 「このような文は嫌です」という修正が、次の文書の文体基準になります。
- 繰り返される入力形式が、スキーマと型になります。
- 頻繁に漏れる検査が、早期検証器と回帰テストになります。
- 毎回手作業で行っていた順序が、コマンド・テンプレート・パイプラインになります。
- 検証済みの新しい経路ができると、一時的なスクリプトと重複経路は整理されます。

## どのように動作しますか？

Agentic Shapingは、次の循環を繰り返します。

| 段階                   | Agentが行うこと                                                        | 残るべき結果        |
| ---------------------- | ------------------------------------------------------------------------ | ----------------------- |
| **Detect**             | 繰り返される説明、ユーザーの修正、嫌だった結果、遅れて発生した失敗や手動判断を検出します。 | 改善候補               |
| **Capture**            | 望まなかった展開と原因、望んだ方向、適用範囲を捉えます。                  | 根拠のある判断基準   |
| **Structure**          | 判断とデータを、記憶・ルーブリック・スキーマ・型・fixtureとして構造化します。 | 再利用可能な契約      |
| **Apply**              | 次の作業の前に関連アセットを見つけ、計画と結果に先に適用します。           | 変化した実行経路      |
| **Verify**             | 実際のファイル・画面・ランタイム・デプロイ結果で確認します。              | 再現可能な証拠        |
| **Simplify / Measure** | 重複と迂回経路をなくし、速度・正確性・再現性の変化を確認します。        | より単純で強いシステム |

中核となる責任は分かれています。

- 意味、文脈、曖昧さ、創造的な選択はAI Agentが担います。
- 繰り返し形式、不変条件、失敗条件、実行順序のように機械的に判定できるものは、コードと契約が担います。

Agentにすべてを記憶させることが目的ではありません。**繰り返される非構造的な判断を発見し、再利用する価値のあるものだけを構造化アセットへ昇格させること**が核心です。

## 文書とソースコードが増えると分析方法も進化します

Agentic Shapingが機能するほど、文書、バイブコーディングのソース、設定、ログ、テストが
増えます。このときAgentに原文全体を毎回読み直させると、サービスの応答とコンテキスト
の制限によって探索が遅くなり、関連情報が長い入力の中に埋もれて分析が不正確になる可能性が
あります。これも構造化すべき反復作業です。

- 繰り返される全体スキャン、長いツール出力、同じシンボル・依存関係の再探索をshapingシグナルとみなします。
- 既存の検索・パーサー・コンパイラー・テストで答えられるものは、まず再利用します。
- 不足している部分だけを、インベントリ、文書/シンボルインデックス、呼び出し・依存・影響グラフ、範囲クエリ、
  整合性検証器へと昇格させます。
- 原文は引き続き権威ある真実のソースです。分析結果には原文の位置とバージョン/ハッシュを残し、
  変更時に更新し、古くなった結果は黙って使用しません。
- Agentにはリポジトリ全体ではなく、現在のタスクに必要な小さな根拠のまとまりを提供し、
  意味・文脈・曖昧さはAgentが判断します。

目標は要約文書をさらに積み重ねることではなく、**原文まで追跡可能で再生成できる
分析サーフェス**を作ることです。次の実行で全体の再分析量・コンテキスト使用量・探索
時間・欠落・再試行が実際に減っているかを測定します。

## 何が変わりますか？

| 作業        | 最初は                              | Agentic Shapingが蓄積された後は                         |
| ----------- | ----------------------------------- | ------------------------------------------------------- |
| コーディング | 症状を直して終わります。             | 原因を型・不変条件・テストに反映し、再発を防ぎます。     |
| 文書        | 文体と構成を毎回もう一度説明します。 | 承認済みの文体・構造・禁止表現を先に適用します。           |
| 分析        | 基準が会話の中だけに残ります。        | 入力スキーマ・判定基準・再現可能な分析手順として残ります。 |
| 画像・動画 | 修正意見が次の制作に引き継がれません。 | スタイルルール・シーン計画・検査基準へとつながります。         |
| デプロイ    | 成功メッセージだけを見て完了とします。 | 実際のURL・証明書・画面・状態を確認するゲートができます。 |

その結果、ユーザーは同じ説明や同じ修正を繰り返す回数が減り、Agentは作業を重ねるほどユーザーの完了基準により早く到達できるようになります。

## 5分で始める

1. 以下のプロンプトを、Agentの持続的な指示に追加します。
   - Codex: グローバルまたはプロジェクトの `AGENTS.md`
   - Claude Code: `CLAUDE.md`
   - GitHub Copilot: リポジトリの指示
   - その他のAgent: プロジェクトの指示またはシステムプロンプト
2. いつもどおり、実際の作業を依頼します。
3. 結果に満足できなければ、理由と望む方向を自然に修正として伝えます。
4. Agentがその修正を現在の結果だけに反映せず、次の実行で使うアセットへ昇格させたか確認します。
5. 完了報告で、実際の検証結果と新たに作成された再利用可能なアセットを確認します。

最初から巨大な自動化システムを作る必要はありません。繰り返される判断を一つ、チェックリストや検証器へ移すことから始めれば十分です。

## 適用プロンプト

以下の内容をそのままコピーして使用できます。

```text
Agentic Shaping v0.3

この作業にはAgentic Shapingを適用してください。

説明や提案だけで終わらせず、現在の依頼を完了させるための行動は常に実行し、再利用価値が確認されたシグナルがある場合は、次回の実行を改善するための行動も併せて実行します。複数の段階が必要な場合は、都合のよい一部だけを選ばず、完了に必要な経路全体を実行します。

作業を計画したり行動を選択したりする際は、①現在の依頼の成果を実際に完成させる行動、②機密情報・権限・形式などの安全境界を守る行動、③再利用価値が確認された場合に限り次回の実行を改善する行動を、それぞれ独立して確認し、該当する行動をすべて明示的に実行します。いずれかを実行したことを理由に、別の項目も暗黙に完了したとはみなしません。

ユーザーが明示的に一度限りで再利用不要と指定した情報・状態・作業については、現在の依頼だけを完了し、必要な秘密情報の除去・安全処理を行います。Agentic Shapingを適用することを理由に、無理に記憶・グローバルルール・再利用可能な資産を作成することはありません。また、保存しないという判断が、現在の依頼の完了に代わることもありません。

1. スコープ・記憶ゲート
   - 開始前に、関連する私の過去の決定、選好、プロジェクトルール、権威ある資料を探し、実際の計画と成果物に反映します。
   - 現在の明示的な依頼は過去の記憶に優先します。
   - ①依頼された成果物を現在のスコープ内で完成させ、②関連する機密性のない選好・スタイルを実際の成果物に適用し、③除外した無関係なプロジェクトルール・別アカウントの権限・資格情報はスコープ外として区別します。3項目は互いに代替できません。
2. シグナルの検知
   - 私が繰り返し説明したこと、修正したこと、望まなかった結果、成功条件、繰り返し発生した失敗、手動判断、高コストな再実行、根拠のない成功・最適化の主張を、別途指示がなくても捉えます。
3. 協働・システム進化の振り分け
   - 個人・プロジェクトの事実・選好・決定を次の作業で想起しようとする依頼は記憶経路に、Agentic Shaping自体を改善しようとする依頼はそのプロンプト・フック・評価資産に、LLM Wiki自体を改善しようとする依頼はそのポリシー・フック・評価資産に、それぞれ区別して振り分けます。
   - Agentic ShapingやLLM Wikiシステムの改善を明示した場合、記憶の保存だけで完了としません。権限の範囲内で該当する権威ある資産を実際に変更し、明示的な進化依頼の発動事例と、通常の記憶依頼がポリシーを変更しないことを示す否定対照群を含む行動評価に合格します。
   - ポリシー・評価変更の依頼では、権威あるポリシーと評価資産、英語・韓国語・日本語・中国語のホームページとREADME、バージョン履歴を、単一の公開バージョンでまとめて更新し、生成・リンク・多言語・静的回帰によってドリフトを防止します。文言・互換性バグの修正はpatch、後方互換性のある機能追加はminor、既存の契約を破る変更はmajorと判定します。
4. 現在の解決 + 次回実行の構造化
   - シグナルがある場合、現在の結果だけを修正して止まりません。現在の作業の完了 → 原因・判断基準の捕捉 → 権威ある資産の更新 → 早期検証・回帰チェック → 実際の結果の確認まで、必要な経路全体を実行します。
   - 適用範囲に応じて、次の形に昇格させます。
   - 選好・判断基準 → 記憶、チェックリスト、ルーブリック
   - 繰り返し入力・データ → スキーマ、型、enum、マニフェスト
   - 繰り返し作業 → テンプレート、コマンド、スクリプト、API、パイプライン
   - 繰り返し発生する失敗 → 不変条件、早期バリデーター、テストfixture
   - 繰り返されるバージョン・パス・設定定数 → 単一の権威ある値に統合し、関連するすべてのハードコーディングを置き換えます。
   - 繰り返し発生するシグナルは、`local`、`project`、`cross-project`、`general-method`で抽象化レベルを判定します。前者2つのレベルは該当するスコープに残し、後者2つだけをプロジェクト・個人情報を除去した汎用スキル候補として合成します。正常・境界・否定事例と禁止行動のチェックにすべて合格した候補だけをSlogs Skillsに`validated-candidate`として提出し、レビュー前には有効化しません。
   - 非構造化→構造化の移行ゲート: durableで機械判定可能なシグナルは、根拠識別子と権威ある場所を持つ構造化資産にし、実際の消費経路に接続します。同じ入力フィンガープリントにおいて、手動判断・再分析量・遅延した失敗・再試行・時間・コンテキスト・欠落のうち1つ以上の事前／事後指標が改善したことを確認します。
   - 状態は`signal-observed`、`structured-and-applied`、`measured-improvement`の3段階として正確に区別します。`structured-and-applied`段階では、凍結した入力、ベースライン群・適用群の根拠、許容される指標、実行コマンドを備えた測定計画まで保存し、Agentic Shapingが対象を改善したと表現できるのは、同じ入力の事前／事後指標が実際に改善した最後の段階に限ります。
   - 文書や記憶に記載しただけのもの、資産を作成しただけのもの、Agentによる改善の主張は、構造化完了の証拠ではありません。実際の消費経路がなければ未適用であり、消費経路はあっても事前／事後の測定がなければ`structured-and-applied`としてのみ報告します。一度限りの判断や創造的な判断は無理に構造化しません。
   - `traceAuthority: orchestrator`のような自己申告文字列は、実行の証拠ではありません。構造化の適用を通過させるには、オーケストレーターが対象リポジトリのrevisionと入力フィンガープリントを固定し、validator・実際のconsumerの成功コマンドと出力ハッシュを収集する必要があります。`measured-improvement`には、同じ実行でベースライン群・適用群だけでなく、事前／事後の値を算出した測定コマンドの実行証拠も必要であり、記録された測定コマンドと出力ハッシュがその証拠と正確に一致しなければなりません。1つでも欠落または不一致があれば、`signal-observed`または`structured-and-applied`を超えて報告しません。
5. コンテキスト拡張ゲート
   - 文書・ソース・ログが大きくなり、全体の読み込みや同じ探索が繰り返される場合は、既存の検索・パーサー・コンパイラー・テストを先に見つけて検証し、作業フローに統合します。不足する分析だけを、インベントリ・インデックス・シンボル／依存グラフ・スコープクエリ・バリデーターとして構造化します。
   - 原文を権威として保持し、分析結果を原文の位置とバージョン／ハッシュに追跡可能にします。staleな結果は更新するか失敗させ、Agentには現在の質問に必要な小さな根拠のまとまりだけを提供します。
6. 判断の境界
   - 意味・曖昧さ・創造性はAgentが判断し、依頼された創作上の変形は実際に作成します。再利用可能な選好はユーザーに確認されたものだけを捉え、確認されたものがないという判断も明示し、一度限りの選択を恒久的なルールにしません。
   - 創作作業でも、明示されたテキスト量・可読性・出力形式・パスを個別に検証します。それ以外の不変条件・失敗条件のような機械判定可能なものはコードと契約で検証します。
7. 実行前・実行後の検証
   - 高コスト・破壊的・デプロイ作業では、入力契約、正確な対象、権限、失敗条件を先に検証します。警告とsilent fallbackを成功として隠しません。
   - 実際のファイル・画面・ランタイム・公式URL・デプロイ状態で完了を確認します。検証済みの新しい経路がある場合は、重複・一時的・迂回経路を整理し、改善効果を時間・コンテキスト・欠落・再試行の変化で測定します。
8. 完了報告
   - 現在の依頼の結果、適用した過去の決定、新たに捉えて構造化した再利用可能な資産、実行した検証、残る制約を区別して知らせます。

現在の依頼と権限を広げず、機密情報・一時的な状態・未検証の推測は保存しません。
```

## このように依頼してみてください

### 作業を始めるとき

```text
この機能を実装して。開始前に、関連する私の決定とプロジェクトルールを先に探して適用し、
繰り返し発生する判断や失敗条件が見つかったら、次の作業で再利用できる型・検証器・テストに昇格させて。
```

### 同じ問題が繰り返されたとき

```text
症状だけを修正せず、なぜ事前に発見できなかったのかを調べて。
次回からは、Agentの手動判断よりも先に、型・スキーマ・不変条件・早期検証器が発見できるようにして。
```

### 作業を終えたとき

```text
今行った作業をAgentic Shapingの観点から振り返って。
今回発見した私の判断基準、繰り返した手動作業、遅れて発見された失敗、新たに作成した再利用資産を区別し、
次回の実行で何を先に適用するか整理して。
```

## 良い結果かどうかを確認する方法

プロンプトにもっともらしい文が含まれているだけで、Agentic Shapingが機能したことにはなりません。次の問いに、実際の証拠で答えられる必要があります。

- Agentはユーザーの修正や繰り返される失敗を自ら発見しましたか？
- 次の作業で再利用できる記憶・ルール・スキーマ・テスト・ツールが生まれましたか？
- durableな非構造シグナルが権威ある構造化資産と実際の利用経路に接続され、同じ入力基準で前後指標が改善しましたか？
- 成果物の規模が大きくなったとき、全体を読み直さなくても必要な根拠を見つけられる構造化された分析基盤がありますか？
- その分析結果は原文の位置・バージョン/ハッシュまで追跡可能で、変更時に更新されますか？
- その資産を次の実行前にまず見つけ出し、実際の計画と結果に適用しましたか？
- 実際のファイル・画面・ランタイム・デプロイ状態で検証しましたか？
- 検証済みの新しい経路ができた後、重複・一時的・迂回経路を整理しましたか？
- 以前より、再説明、手動判断、再試行、または遅れて発生する失敗が減りましたか？

このリポジトリの `evals/` では、公開プロンプトを適用していないベースライン群と適用群に同じタスクを与え、一般的な作業品質とAgentic Shaping固有の発動を分けて比較します。

- Agentic Shaping差別化評価: 26組のペアシナリオ、GPT-5.6 Luna Max 52回実行
- 固有行動の完全達成: ベースライン群16/26(61.5%)、適用群25/26(96.2%)
- 固有行動の詳細基準: ベースライン群82/105(78.1%)、適用群104/105(99.0%)
- 初見の最終holdout: ベースライン群3/5(60%)、適用群5/5(100%)
- 現在のタスク完了: 両群27/27、禁止行動: 両群0件
- 一般品質・安全性の回帰: ベースライン群94/98(95.9%)、適用群96/98(98.0%)、禁止行動0件
- 実際のファイル実行評価: 両群6/6 (1つのタスクに回帰がないことだけを確認し、プロンプトの優位性を証明するものではありません)

評価自体もAgentic Shapingの対象です。今回の検証では、少ないサンプル数、ベースライン群への指示汚染、曖昧な事例、繰り返し発生する失敗、全体再実行のコスト、timeoutをシグナルとして捉え、次の資産へ昇格させました。

- 一般品質の回帰とAgentic Shapingの差別化スコアを分離
- 開発セット、結果を確認済みのholdout、初見の最終holdoutを区別
- 失敗事例フィルターで先に再生してから、全体の回帰を実行
- 失敗の反復結果を破棄せず、iteration JSONと観察ドキュメントとして保存
- suite・プロンプト・モデル・事例一覧のハッシュが一致する場合のみcheckpoint/resume
- timeoutをプロンプトの失敗と分離し、1回だけ再試行
- `tests/` 配下の合格テストを見落とした採点器の不具合を保存し、再帰探索で修正

機械的に判定可能な実行順序の失敗に対しては、`AS-BI-001` 行動インターロック契約と参照用 hook も提供します。ハーネスが選択した安全な並行作業が残っている場合、最初の wait/poll から、正確な次の作業の新しい証拠が先行していないすべての無操作 poll をブロックし、60,000ms の待機予算を超えた poll も独立してブロックします。時間はモデルの主張ではなく、ハーネスが提供する単調時間の証拠であり、訂正対話の原文はプロンプトに含めません。`node .\evals\verify-behavioral-interlock.mjs` で 34-case の決定論的ゲートを実行できます。実際の hook のエントリポイントは `node .\evals\behavioral-interlock.mjs --trace <runtime-trace.json>` であり、trace なしで直接実行した場合は、何も検査していないのに成功したように見えないよう、exit 64 で終了します。ランタイムは同じモジュールを副作用なしで import し、プロセス内で判定することもできます。これは再利用可能な hook であり、すべての Agent 製品にすでにグローバルに組み込まれているという主張ではありません。ハード強制にはランタイムとオーケストレーターの連携が必要です。

誤った同伴作業の証拠に対しては、コードだけでなく、修正案内と契約で許可される `allowedEvidenceKinds` も併せて返します。この案内は誤字や統合エラーを減らしますが、状態メッセージ・記憶の保存・宣言されていない証拠を同伴作業へと昇格させることはありません。
許可される enum の全一覧は `artifact`、`contract-review`、`fixture-design`、`inventory`、`low-load-analysis`、`verification`、`system-evolution-audit`、`system-evolution-contract` です。ハーネスは最初の poll の前にこの一覧で trace を検証できるため、拒否された実行を通じて正確な綴りを後から確認する必要はありません。

長期作業の状態で一つの目標軸だけを報告したり、根拠のない全体パーセンテージを作成したりする失敗に対して、`AS-PRG-001` 多軸進捗率契約と参照 hook を提供します。ハーネスが宣言したすべての軸を、それぞれ `完了/総件数・正確なパーセンテージ・失敗分類・現在の段階・次の検証段階` として報告する必要があります。権威ある分母がまだ存在しない場合は、パーセンテージを推定せず、現在の測定範囲と分母が確定していない理由を別途示します。異なる分母を一つの全体パーセンテージに統合して作業軸を隠すことも阻止します。`node .\evals\verify-progress-report.mjs` で正常系・境界系・負の対照群11件を実行し、`progress-report.mjs --trace` は、欠落した stdlib 軸、誤って計算された比率、推定分母を exit 2 で終了させます。

`AS-BI-001`は、Agentic ShapingまたはSlogs LLM Wikiの監査・契約実装を安全な付随作業として使用する場合、対象システムと実際のアセットの根拠を併せて要求します。進捗メッセージ、記憶のcapture/write、モデルの主張だけでは、待機予算を更新できません。一般的な`artifact`証拠でも、実際のアセットパスを`artifactEvidence`に任意で記録できますが、記録する場合は空または空白のみの項目を許可しません。拡張された決定論的ゲートは34個であり、既存の入力変更や競合する高負荷作業の禁止もそのまま維持されます。

高コストゲートの前に、変更した不変条件のdownstream consumerの一部だけを修正してしまう失敗に対して、`AS-EG-001`高コストゲート契約と参照hookを提供します。60,000ms以上と見積もられるゲートは、変更契約ごとにハーネスが宣言したconsumer集合を正確に網羅する合格監査、正・負のcheap probe、preflight前後で同一の入力SHA-256がある場合にのみ開始できます。モデル作成の証拠、consumerの欠落・重複、片側だけまたは失敗したprobe、入力drift、未知フィールドはfail closedになります。`node .\evals\verify-expensive-gate.mjs`で11ケースの決定論的ゲートを実行し、`--evidence`の許可exit 0・遮断exit 2をオーケストレーターへ接続できます。これは参照hookであり、ハード強制にはハーネスが権威イベントからconsumer・監査・probe証拠を構成する必要があります。

協働対象を誤って記憶経路へ送る失敗に対し、`AS-CR-001`協働ルーティング契約と参照hookを提供します。個人・プロジェクト記憶、Agentic Shaping進化、Slogs LLM Wikiシステム進化を分離します。`in-progress`段階では主作業が未完了であることを保ちつつ、各システムに事前評価契約と監査または実変更証拠を要求し、`final`段階だけが現在作業の完了、実際のprompt/hook変更、行動検証を要求します。12件の対照を`node .\evals\verify-collaboration-routing.mjs`で実行できます。

### v0.3 技術メモ

`AS-SA-001`は、反復シグナルの抽象化レベルを`local`、`project`、`cross-project`、`general-method`のいずれかとして最初に判定します。`local`と`project`は共有登録をブロックし、異なる適用領域が十分に確認された`cross-project`と`general-method`のみを、プロジェクト識別子や個人への参照を除去した汎用スキルパッケージとして合成します。個人情報、プロジェクト機密、資格情報、秘密情報、安全でないパス、不十分な一般化、正常・境界・否定評価の欠落が一つでもあれば、すべてクローズ状態で失敗させます。現在、抽象化・安全性検査は25/25に合格しており、Slogs Skillsの`skill_registry_submit_candidate`入力および`validated-candidate`状態と一致しています。ただし、運用Slogs MCPにはまだデプロイされていないため、実際の候補登録は実行していません。したがって、現在の状態は`structured-and-applied`であり、運用適用の完了や効果の改善とは表現しません。

`AS-PS-001`は重要なポリシー・評価変更の公開同期を担います。単一の権威あるバージョンでポリシー・評価、4言語のホームページ、4言語のREADME、`CHANGELOG.md`を併せて更新し、バージョン・数値・契約・生成結果に不一致があれば、pushとデプロイの前に失敗します。文言・互換性バグの修正は`patch`、後方互換性のある機能追加は`minor`、既存の公開契約を破る変更は`major`です。今回のスキル発見・Slogs候補連携は後方互換性のある機能追加であるため、`0.2.0 → 0.3.0`として記録しました。

## LLM Wikiとともに使う

Agentic Shapingは、現在の会話とプロジェクト指示だけでも開始できます。しかし、会話が終わると、それまでに見つかったコンテキストが失われる可能性があります。

- **LLM Wikiとともに使うと、より効果的に機能します。** 修正・好み・判断基準を長期的に保持し、次のタスクの前に再利用できます。
- **Slogs LLM Wikiとともに使うと、さらに効果的に機能します。** 作業前の先行想起、意図修正シグナルの捕捉、グローバル原則とプロジェクト記憶の分離、根拠を保持する更新フローを併用できます。

重要なのは、たくさん保存することではありません。関連する記憶を作業前に見つけ、計画と結果に実際に適用し、検証したうえで再び更新する循環が重要です。

## 安全境界

Agentic Shapingは、Agentの権限を拡大する方法ではありません。

- 現在のユーザーが要求した範囲と権限を超えません。
- 機密情報、トークン、パスワード、一回限りのログを記憶として残しません。
- 現在の要求と過去の記憶が衝突する場合は、現在の要求を優先します。
- 一般原則とプロジェクト固有の構文・契約・検証基準を混同しません。
- 自動化できるという理由だけで、創造的な判断まで機械的なルールに矮小化しません。
