# Agentic Shaping

## 为什么需要它？

与 AI 一起工作时，第一份结果会很快出现。但如果下一项工作还要重新说明相同的文风、再次修改之前说过不喜欢的结果，并且事后又发现已经经历过的失败，速度就无法积累。

Agentic Shaping 不会停留在一个好结果上。它会在每次工作时，**逐步改进负责创造下一个结果的 Agent 以及执行系统本身**。

- “我不喜欢这样的句子”这一纠正，会成为下一份文档的文风标准。
- 重复出现的输入格式会成为 schema 和类型。
- 经常遗漏的检查会成为早期验证器和回归测试。
- 每次都要手动执行的顺序会成为命令·模板·流水线。
- 验证过的新路径出现后，临时脚本和重复路径会被清理。

## 它是如何工作的？

Agentic Shaping 会重复以下循环。

| 阶段                   | Agent 的工作                                                            | 应留下的结果          |
| ---------------------- | ------------------------------------------------------------------------ | ----------------------- |
| **Detect**             | 检测重复解释、用户纠正、不喜欢的结果、延迟失败和手动判断。                 | 改进候选              |
| **Capture**            | 捕捉不希望的展开及其原因、期望方向和适用范围。                             | 有依据的判断标准      |
| **Structure**          | 将判断和数据结构化为记忆·rubric·schema·类型·fixture。                      | 可复用的契约          |
| **Apply**              | 在下一项工作开始前找到相关资产，并优先应用到计划和结果中。                  | 改变后的执行路径      |
| **Verify**             | 通过实际文件·屏幕·运行时·部署结果进行确认。                                | 可复现的证据          |
| **Simplify / Measure** | 消除重复和绕行路径，并确认速度·准确度·可复现性的变化。                      | 更简单、更强的系统    |

核心职责是分开的。

- 意义、上下文、歧义和创造性选择由 AI Agent 负责。
- 重复格式、不变量、失败条件和执行顺序等可以机械判定的内容由代码和契约负责。

这并不是让 Agent 记住一切。核心是**发现重复的非结构化判断，并将只有值得复用的内容升级为结构化资产**。

## 文档和源代码变大后，分析方式也会进化

Agentic Shaping 越有效，文档、vibe coding 源代码、配置、日志和测试就会
越多。此时如果让 Agent 每次都重新阅读全部原文，受服务响应和上下文
限制影响，探索会变慢，相关信息也可能埋在长输入中，导致分析不准确。
这同样是一项需要结构化的重复工作。

- 将反复的全量扫描、冗长的工具输出，以及对相同符号·依赖关系的重复探索视为 shaping 信号。
- 能通过现有搜索·解析器·编译器·测试回答的问题，优先复用现有工具。
- 仅将不足的部分升级为资产清单、文档/符号索引、调用·依赖·影响图、范围查询、
  一致性验证器。
- 原文始终是权威事实源。分析结果中保留原文位置和版本/哈希，并在发生变更时更新，
  过时的结果不会被静默使用。
- 不向 Agent 提供整个存储库，而是提供当前任务所需的小型证据集，
  意义·上下文·歧义由 Agent 判断。

目标不是继续堆积摘要文档，而是建立**可追溯到原文且能够重新生成的
分析表面**。在下一次执行中，测量全量重新分析量·上下文使用量·探索
时间·遗漏·重试是否确实减少。

## 会有什么不同？

| 工作        | 起初                                | Agentic Shaping 积累之后                                  |
| ----------- | ----------------------------------- | ------------------------------------------------------- |
| 编码        | 修复症状后就结束。                  | 将原因反映到类型·不变量·测试中，防止再次发生。              |
| 文档        | 每次重新说明文风和结构。            | 优先应用已批准的文风·结构·禁用表达。                      |
| 分析        | 标准只留在对话中。                  | 留下输入 schema·判断标准·可复现的分析流程。                |
| 图像·视频   | 修改意见在下一次制作中消失。        | 延续为风格规则·场景计划·审查标准。                        |
| 部署        | 只看到成功消息就算完成。            | 增加确认实际 URL·证书·画面·状态的门控。                   |

结果是，用户不必反复进行相同的说明和修改，而 Agent 会随着工作不断重复，更快达到用户的完成标准。

## 5 分钟内开始

1. 将下面的提示词加入使用该 Agent 的持续指令中。
   - Codex：全局或项目 `AGENTS.md`
   - Claude Code: `CLAUDE.md`
   - GitHub Copilot：存储库指令
   - 其他 Agent：项目指令或系统提示词
2. 像平常一样请求实际工作。
3. 如果不喜欢结果，自然地说明原因和期望方向进行纠正。
4. 确认 Agent 是否没有只将该纠正应用于当前结果，而是将其升级为下一次执行可用的资产。
5. 在完成报告中确认实际验证结果和新创建的可复用资产。

不必从一开始就构建庞大的自动化系统。从将一个重复判断转移到清单或验证器开始即可。

## 应用提示词

可以原样复制下面的内容使用。

```text
Agentic Shaping v0.2

请将 Agentic Shaping 应用于这项工作。

不要只提供说明或建议；凡是能够完成当前请求的行动，都必须始终执行。当发现具有复用价值的信号时，还要同时执行能够改进下一次运行的行动。若需要多个步骤，不要只挑选其中方便的部分，而要执行完成任务所需的完整路径。

在规划工作或选择行动时，请分别独立确认：① 真正完成当前请求结果的行动；② 遵守敏感信息、权限、格式等安全边界的行动；③ 仅在确认具有复用价值时，改进下一次运行的行动，并明确执行所有适用的行动。不能因为完成了其中一项，就认为其他项也已隐式完成。

如果用户明确表示某项信息、状态或工作是一次性的、无需复用，则只完成当前请求，并执行必要的秘密移除与安全处理。不要因为应用 Agentic Shaping，就强行创建记忆、全局规则或可复用资产；不保存的判断也不能替代完成当前请求。

1. 范围与记忆门禁
   - 开始前，查找与当前任务相关的我的过往决定、偏好、项目规则和权威资料，并实际反映到计划和产出物中。
   - 当前明确请求优先于过去的记忆。
   - ① 在当前范围内完成请求的产出物；② 将相关的非敏感偏好与风格实际应用到产出物中；③ 明确区分被排除的无关项目规则、其他账户权限和凭据属于范围之外。这三项不可相互替代。
2. 信号感知
   - 无需额外指示，捕捉我反复解释过的内容、做过的修正、不喜欢的结果、成功条件、反复失败、手动判断、昂贵的重新执行，以及没有依据却声称成功或完成优化的情况。
3. 当前解决 + 下一次运行的结构化
   - 发现信号后，不要只修正当前结果就停下。执行完成当前工作 → 捕捉原因与判断标准 → 更新权威资产 → 进行早期验证与回归检查 → 确认实际结果所需的完整路径。
   - 根据应用范围，将其提升为以下形式。
   - 偏好与判断标准 → 记忆、检查清单、评估量规
   - 重复输入与数据 → 架构、类型、enum、清单
   - 重复工作 → 模板、命令、脚本、API、流水线
   - 重复失败 → 不变量、早期验证器、测试 fixture
   - 重复出现的版本、路径和配置常量 → 统一为单一权威值，并替换所有相关硬编码
4. 上下文扩展门禁
   - 当文档、源代码和日志变大，导致反复进行全文阅读和相同探索时，先发现并验证现有的搜索、解析器、编译器和测试，将其整合进工作流。只有不足的分析才结构化为清单、索引、符号/依赖图、范围查询和验证器。
   - 保留原文作为权威来源，并使分析结果能够追溯到原文位置和版本/哈希。过期结果必须更新或使其失败，并且只向 Agent 提供当前问题所需的小型证据集合。
5. 判断边界
   - 语义、歧义和创造性由 Agent 判断；对于请求的创作变体，要实际生成。只有经过用户确认的复用偏好才能被捕捉；也要明确说明尚未确认的判断，不要把一次性选择变成永久规则。
   - 即使是创作任务，也要单独验证明确指定的文本数量、可读性、输出格式和路径。除此之外，凡是像不变量、失败条件一样可以由机器判定的内容，都要通过代码和契约进行验证。
6. 执行前后验证
   - 对高成本、破坏性或部署类工作，先验证输入契约、准确目标、权限和失败条件。不要用警告和 silent fallback 掩盖失败并将其伪装成成功。
   - 通过实际文件、界面、运行时、官方 URL 和部署状态确认完成情况。若存在经过验证的新路径，就清理重复、临时和绕行路径，并通过时间、上下文、遗漏和重试的变化衡量改进效果。
7. 完成报告
   - 区分并告知当前请求的结果、应用的过往决定、新捕捉并结构化的可复用资产、执行的验证以及剩余限制。

不要扩大当前请求和权限范围，不要保存敏感信息、一次性状态或未经验证的推测。
```

## 试着这样请求

### 开始工作时

```text
请实现此功能。开始前先查找并应用与之相关的我的决定和项目规则，
如果发现重复的判断或失败条件，请将其提升为可在后续工作中复用的类型、验证器和测试。
```

### 同一个问题反复出现时

```text
不要只修复症状，请找出为什么没能更早发现问题。
从今以后，让类型、模式、不变量和早期验证器先于 Agent 的手动判断发现问题。
```

### 完成工作时

```text
请从 Agentic Shaping 的角度回顾刚才的工作。
区分本次发现的我的判断标准、重复进行的手动工作、延迟发现的失败，以及新创建的可复用资产，
整理下一次执行时应优先应用哪些内容。
```

## 如何确认结果是否良好

提示词中包含看似合理的句子，并不意味着 Agentic Shaping 已经生效。必须能够用实际证据回答以下问题。

- Agent 是否自行发现了用户的纠正或重复失败？
- 是否产生了可以在下一项工作中复用的记忆·规则·schema·测试·工具？
- 当产出规模变大时，是否已经建立了无需重新通读全部内容即可找到所需依据的结构化分析界面？
- 这些分析结果是否可以追溯到原文位置和版本/哈希，并会在变更时更新？
- 是否在下一次执行前先找到这些资产，并将其实际应用到计划和结果中？
- 是否已通过实际文件、界面、运行时和部署状态完成验证？
- 经过验证的新路径建立后，是否清理了重复、临时和绕行路径？
- 与之前相比，是否减少了重新解释、手动判断、重试或延迟失败？

本仓库的 `evals/` 会向未应用公开提示词的基线组和应用组提供相同任务，并将常规任务质量与 Agentic Shaping 的独有触发效果分开比较。

- Agentic Shaping 差异化评估：26 个配对场景，GPT-5.6 Luna Max 执行 52 次
- 独有行为完全通过：基线组 16/26(61.5%)，应用组 25/26(96.2%)
- 独有行为细分标准：基线组 82/105(78.1%)，应用组 104/105(99.0%)
- 首次见到的最终 holdout：基线组 3/5(60%)，应用组 5/5(100%)
- 当前任务完成：双方均为 27/27；禁止行为：双方均为 0 项
- 常规质量·安全回归：基线组 94/98(95.9%)，应用组 96/98(98.0%)，禁止行为 0 项
- 实际文件执行评估：双方均为 6/6（仅确认某项任务没有回归，不证明提示词的优势）

评估本身也属于 Agentic Shaping 的对象。在本次验证中，我们将小样本、基线组指令污染、模糊案例、重复失败、完整重跑成本和 timeout 捕捉为信号，并将其提升为后续资产。

- 分离常规质量回归与 Agentic Shaping 差异化得分
- 区分开发集、看过结果的 holdout，以及首次见到的最终 holdout
- 先通过失败案例筛选器重放，再执行完整回归
- 不丢弃重复失败的结果，而是将其保存在 iteration JSON 和观察文档中
- 仅当 suite·提示词·模型·案例列表的哈希一致时才 checkpoint/resume
- 将 timeout 与提示词失败分开，并且只重试一次
- 保留遗漏 `tests/` 下通过测试的评分器缺陷，并通过递归搜索进行修正

已将确认的最终提示词行为契约同步到 Slogs LLM Wiki 的韩语和英语运行时政策中。最终政策版本为 `2026.08.25.3`，明确执行以下内容。

- 独立确认当前结果已完成、敏感信息·权限·格式·范围受到保护，以及基于 durable 信号改进下一次执行
- 对明确的一次性任务，不强行创建记忆·全局规则·可复用资产
- durable 信号完成从捕捉原因·标准，到建立权威资产、进行早期验证·回归，再到确认实际结果的完整流程
- 将重复的版本·路径·配置整合为单一权威来源，并替换所有相关硬编码

[Slogs LLM Wiki 最终韩语政策](https://slogs.dev/prompts/slogs-mcp.ko.md)和[版本 endpoint](https://slogs.dev/prompts/slogs-mcp.version)可用于确认同步状态。

我们没有只检查是否包含相关措辞，而是将实时政策 URL 直接注入 Luna Max，执行了 5 个配对回归和 10 次 Agent 运行。独有行为从基线组的 18/20(90%) 提升至政策应用组的 20/20(100%)，两组的禁止行为均为 0 项。该案例已经属于公开的回归集，不应解读为新的未公开 holdout。原始内容保存在 `evals/slogs-policy-smoke-luna-max.json` 中。

该结果是 GPT-5.6 Luna Max 在固定集上的单次运行所得的技术统计，不是总体估计，也不代表对所有模型·工具环境的保证。应用组在版本漂移中也漏掉了一个行为。提示词发生变化后，必须重新执行相同的评估和实际运行门禁。

## 与 LLM Wiki 一起使用

Agentic Shaping 仅凭当前对话和项目指引即可开始使用。但对话结束后，期间发现的上下文可能会消失。

- **与 LLM Wiki 一起使用，效果会更好。** 可以长期保留更正、偏好和判断标准，并在下一项工作开始前再次取用。
- **与 Slogs LLM Wiki 一起使用，效果会再上一个台阶。** 可以同时进行工作前的主动回忆、捕捉意图修正信号、分离全局原则与项目记忆，以及保留依据的更新流程。

重要的不是存储很多内容，而是在工作开始前找到相关记忆，将其实际应用到计划和结果中，并在验证后再次更新的循环。

## 安全边界

Agentic Shaping 不是扩大 Agent 权限的方法。

- 不超出当前用户请求的范围和权限。
- 不将敏感信息、令牌、密码和一次性日志保存为记忆。
- 当前请求与过往记忆冲突时，以当前请求为优先。
- 不混淆通用原则与项目特定的语法·契约·验证标准。
- 不会仅因某件事可以自动化，就把创造性判断也缩减为机器规则。
