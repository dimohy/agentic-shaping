## 为什么需要它？

与 AI 一起工作时，第一份结果会很快出现。但如果下一项工作还要重新说明相同的文风、再次修改之前说过不喜欢的结果，并且事后又发现已经经历过的失败，速度就无法积累。

Agentic Shaping 不会停留在一个好结果上。它会在每次工作时，**逐步改进负责创造下一个结果的 Agent 以及执行系统本身**。

- “我不喜欢这样的句子”这一纠正，会成为下一份文档的文风标准。
- 重复出现的输入格式会成为 schema 和类型。
- 经常遗漏的检查会成为早期验证器和回归测试。
- 每次都要手动执行的顺序会成为命令·模板·流水线。
- 验证过的新路径出现后，临时脚本和重复路径会被清理。

## 它是如何工作的？

Agentic Shaping 会重复以下循环。

| 阶段                   | Agent 的工作                                                            | 应留下的结果          |
| ---------------------- | ------------------------------------------------------------------------ | ----------------------- |
| **Detect**             | 检测重复解释、用户纠正、不喜欢的结果、延迟失败和手动判断。                 | 改进候选              |
| **Capture**            | 捕捉不希望的展开及其原因、期望方向和适用范围。                             | 有依据的判断标准      |
| **Structure**          | 将判断和数据结构化为记忆·rubric·schema·类型·fixture。                      | 可复用的契约          |
| **Apply**              | 在下一项工作开始前找到相关资产，并优先应用到计划和结果中。                  | 改变后的执行路径      |
| **Verify**             | 通过实际文件·屏幕·运行时·部署结果进行确认。                                | 可复现的证据          |
| **Simplify / Measure** | 消除重复和绕行路径，并确认速度·准确度·可复现性的变化。                      | 更简单、更强的系统    |

核心职责是分开的。

- 意义、上下文、歧义和创造性选择由 AI Agent 负责。
- 重复格式、不变量、失败条件和执行顺序等可以机械判定的内容由代码和契约负责。

这并不是让 Agent 记住一切。核心是**发现重复的非结构化判断，并将只有值得复用的内容升级为结构化资产**。

## 文档和源代码变大后，分析方式也会进化

Agentic Shaping 越有效，文档、vibe coding 源代码、配置、日志和测试就会
越多。此时如果让 Agent 每次都重新阅读全部原文，受服务响应和上下文
限制影响，探索会变慢，相关信息也可能埋在长输入中，导致分析不准确。
这同样是一项需要结构化的重复工作。

- 将反复的全量扫描、冗长的工具输出，以及对相同符号·依赖关系的重复探索视为 shaping 信号。
- 能通过现有搜索·解析器·编译器·测试回答的问题，优先复用现有工具。
- 仅将不足的部分升级为资产清单、文档/符号索引、调用·依赖·影响图、范围查询、
  一致性验证器。
- 原文始终是权威事实源。分析结果中保留原文位置和版本/哈希，并在发生变更时更新，
  过时的结果不会被静默使用。
- 不向 Agent 提供整个存储库，而是提供当前任务所需的小型证据集，
  意义·上下文·歧义由 Agent 判断。

目标不是继续堆积摘要文档，而是建立**可追溯到原文且能够重新生成的
分析表面**。在下一次执行中，测量全量重新分析量·上下文使用量·探索
时间·遗漏·重试是否确实减少。

## 会有什么不同？

| 工作        | 起初                                | Agentic Shaping 积累之后                                  |
| ----------- | ----------------------------------- | ------------------------------------------------------- |
| 编码        | 修复症状后就结束。                  | 将原因反映到类型·不变量·测试中，防止再次发生。              |
| 文档        | 每次重新说明文风和结构。            | 优先应用已批准的文风·结构·禁用表达。                      |
| 分析        | 标准只留在对话中。                  | 留下输入 schema·判断标准·可复现的分析流程。                |
| 图像·视频   | 修改意见在下一次制作中消失。        | 延续为风格规则·场景计划·审查标准。                        |
| 部署        | 只看到成功消息就算完成。            | 增加确认实际 URL·证书·画面·状态的门控。                   |

结果是，用户不必反复进行相同的说明和修改，而 Agent 会随着工作不断重复，更快达到用户的完成标准。

## 5 分钟内开始

1. 将下面的提示词加入使用该 Agent 的持续指令中。
   - Codex：全局或项目 `AGENTS.md`
   - Claude Code: `CLAUDE.md`
   - GitHub Copilot：存储库指令
   - 其他 Agent：项目指令或系统提示词
2. 像平常一样请求实际工作。
3. 如果不喜欢结果，自然地说明原因和期望方向进行纠正。
4. 确认 Agent 是否没有只将该纠正应用于当前结果，而是将其升级为下一次执行可用的资产。
5. 在完成报告中确认实际验证结果和新创建的可复用资产。

不必从一开始就构建庞大的自动化系统。从将一个重复判断转移到清单或验证器开始即可。

## 应用提示词

可以原样复制下面的内容使用。

```text
Agentic Shaping v0.3

请将 Agentic Shaping 应用于此任务。

不要只提供说明或建议；始终执行能够完成当前请求的操作，并在确认存在可复用价值的信号时，同时执行能够改进后续运行的操作。如果需要多个步骤，不要只选择其中方便的部分，而要执行完成任务所需的完整路径。

在规划任务或选择操作时，应分别独立确认并明确执行以下各项：① 实际完成当前请求结果的操作；② 遵守敏感信息、权限、格式等安全边界的操作；③ 仅在确认存在可复用价值时改进后续运行的操作。不要因为执行了一项，就默认另一项也已隐式完成。

对于用户明确表示是一次性且无需复用的信息、状态或任务，只完成当前请求，并执行必要的秘密清除与安全处理。不要因为应用 Agentic Shaping 就强行创建记忆、全局规则或可复用资产；判断不保存也不能替代完成当前请求。

1. 范围·记忆门控
   - 开始前，查找与任务相关的我过去的决定、偏好、项目规则和权威资料，并将其实际反映到计划和产出中。
   - 当前明确请求优先于过去的记忆。
   - 明确区分以下三项：① 在当前范围内完成请求的产出；② 将相关的非敏感偏好·风格实际应用于产出；③ 将排除的无关项目规则·其他账户权限·凭据标记为范围外。这三项不能相互替代。
2. 信号检测
   - 无需额外指示，捕捉我反复解释或修改过的内容、不喜欢的结果、成功条件、反复失败、手动判断、高成本重运行，以及没有依据却声称已成功或已完成优化的情况。
3. 协作·系统演进路由
   - 将试图在后续任务中回忆个人·项目事实·偏好·决定的请求路由到记忆路径；将改进 Agentic Shaping 本身的请求路由到其提示词·钩子·评估资产；将改进 LLM Wiki 本身的请求路由到其政策·钩子·评估资产，并彼此区分。
   - 明确要求改进 Agentic Shaping 或 LLM Wiki 系统时，不能仅通过保存记忆来完成。应在权限范围内实际修改相应的权威资产，并通过行为评估，其中包括明确演进请求的触发案例，以及普通记忆请求不会改变政策的负面对照组。
   - 对政策·评估变更请求，应在一个公开版本中同时更新权威政策和评估资产、英语·韩语·日语·中文主页和 README、版本历史，并通过生成·链接·多语言·静态回归阻止漂移。文字·兼容性 bug 修复判定为 patch，向后兼容的功能添加判定为 minor，破坏现有契约的变更判定为 major。
4. 当前解决 + 后续运行结构化
   - 发现信号后，不要只修复当前结果就停止。执行完整路径：完成当前工作 → 捕捉原因·判断标准 → 更新权威资产 → 执行提前验证·回归检查 → 确认实际结果。
   - 根据应用范围提升为以下形式。
   - 偏好·判断标准 → 记忆、检查清单、评分标准
   - 重复输入·数据 → 模式、类型、enum、清单
   - 重复工作 → 模板、命令、脚本、API、流水线
   - 重复失败 → 不变量、提前验证器、测试 fixture
   - 重复出现的版本·路径·配置常量 → 统一为单一权威值，并替换所有相关硬编码
   - 使用 `local`、`project`、`cross-project`、`general-method` 判定重复信号的抽象层级。前两个层级保留在相应范围内，仅将后两个层级合成为移除项目·个人信息的通用技能候选。只有通过正常·边界·负面案例和禁止行为检查的候选，才提交到 Slogs Skills 并标记为 `validated-candidate`；审核前不得激活。
   - 非结构化→结构化转换门控：将持久且可由机器判定的信号构建为带有证据标识符和权威位置的结构化资产，连接到实际消费路径，并确认在相同输入指纹下，手动判断·重新分析量·延迟失败·重试次数·耗时·上下文·遗漏中的至少一项前后指标得到改善。
   - 将状态严格区分为 `signal-observed`、`structured-and-applied`、`measured-improvement` 三个阶段。`structured-and-applied` 阶段还必须保留包含冻结输入、基准组·应用组证据、允许指标和执行命令的测量计划；只有相同输入的前后指标实际改善的最后阶段，才能表述为 Agentic Shaping 改进了目标。
   - 写入文档或记忆、仅创建资产，以及 Agent 声称已改进，都不是结构化完成的证据。没有实际消费路径即视为未应用；存在消费路径但没有前后测量时，只能报告为 `structured-and-applied`。不要强行将一次性·创造性判断结构化。
   - `traceAuthority: orchestrator` 等自我声明字符串不是执行证据。要通过结构化应用，编排器必须固定目标存储库 revision 和输入指纹，并收集 validator·实际 consumer 的成功命令及输出哈希。`measured-improvement` 除了要求同一次运行中的基准组·应用组，还要求提供生成前后值的测量命令执行证据；记录的测量命令和输出哈希必须与该证据准确一致。缺少或不一致任何一项时，不得报告为高于 `signal-observed` 或 `structured-and-applied` 的状态。
5. 上下文扩展门控
   - 当文档·源代码·日志变大，导致反复进行完整读取和相同探索时，先发现并验证现有搜索·解析器·编译器·测试，然后将其整合到工作流中。仅将不足的分析结构化为清单·索引·符号/依赖图·范围查询·验证器。
   - 保留原文作为权威来源，并使分析结果能够追溯到原文位置和版本/哈希。过时结果应更新或使其失败，并只向 Agent 提供当前问题所需的小型证据集。
6. 判断边界
   - 由 Agent 判断含义·歧义·创造性，并实际制作所请求的创作变体。只捕捉已向用户确认的可复用偏好；也要明确说明没有已确认偏好这一判断，不要将一次性选择变成永久规则。
   - 即使在创作任务中，也要单独验证明确指定的文本数量·可读性·输出格式·路径。其余不变量·失败条件等可由机器判定的内容，应通过代码和契约验证。
7. 执行前·后验证
   - 对高成本·破坏性·部署操作，先验证输入契约、准确目标、权限和失败条件。不要用警告和 silent fallback 隐藏失败并将其视为成功。
   - 通过实际文件·屏幕·运行时·官方 URL·部署状态确认完成。如果存在已验证的新路径，应清理重复·临时·绕过路径，并通过耗时·上下文·遗漏·重试变化衡量改进效果。
8. 完成报告
   - 区分并告知当前请求的结果、应用的过去决定、新捕捉·结构化的可复用资产、执行的验证以及剩余限制。

不要扩大当前请求和权限范围，不要保存敏感信息·一次性状态·未经验证的推测。
```

## 如何确认结果是否良好

提示词中包含看似合理的句子，并不意味着 Agentic Shaping 已经生效。必须能够用实际证据回答以下问题。

- Agent 是否自行发现了用户的纠正或重复失败？
- 是否产生了可以在下一项工作中复用的记忆·规则·schema·测试·工具？
- durable 的非结构化信号是否已连接到权威的结构化资产和实际消费路径，并且相同输入标准下的前后指标得到改善？
- 当产出规模变大时，是否已经建立了无需重新通读全部内容即可找到所需依据的结构化分析界面？
- 这些分析结果是否可以追溯到原文位置和版本/哈希，并会在变更时更新？
- 是否在下一次执行前先找到这些资产，并将其实际应用到计划和结果中？
- 是否已通过实际文件、界面、运行时和部署状态完成验证？
- 经过验证的新路径建立后，是否清理了重复、临时和绕行路径？
- 与之前相比，是否减少了重新解释、手动判断、重试或延迟失败？

本仓库的 `evals/` 会向未应用公开提示词的基线组和应用组提供相同任务，并将常规任务质量与 Agentic Shaping 的独有触发效果分开比较。

- Agentic Shaping 差异化评估：26 个配对场景，GPT-5.6 Luna Max 执行 52 次
- 独有行为完全通过：基线组 16/26(61.5%)，应用组 25/26(96.2%)
- 独有行为细分标准：基线组 82/105(78.1%)，应用组 104/105(99.0%)
- 首次见到的最终 holdout：基线组 3/5(60%)，应用组 5/5(100%)
- 当前任务完成：双方均为 27/27；禁止行为：双方均为 0 项
- 常规质量·安全回归：基线组 94/98(95.9%)，应用组 96/98(98.0%)，禁止行为 0 项
- 实际文件执行评估：双方均为 6/6（仅确认某项任务没有回归，不证明提示词的优势）

评估本身也属于 Agentic Shaping 的对象。在本次验证中，我们将小样本、基线组指令污染、模糊案例、重复失败、完整重跑成本和 timeout 捕捉为信号，并将其提升为后续资产。

- 分离常规质量回归与 Agentic Shaping 差异化得分
- 区分开发集、看过结果的 holdout，以及首次见到的最终 holdout
- 先通过失败案例筛选器重放，再执行完整回归
- 不丢弃重复失败的结果，而是将其保存在 iteration JSON 和观察文档中
- 仅当 suite·提示词·模型·案例列表的哈希一致时才 checkpoint/resume
- 将 timeout 与提示词失败分开，并且只重试一次
- 保留遗漏 `tests/` 下通过测试的评分器缺陷，并通过递归搜索进行修正

对于可由机器判定的执行顺序失败，我们还提供 `AS-BI-001` 行为互锁契约和参考 hook。如果还存在由 harness 选定的安全并行任务，则从第一个 wait/poll 开始，阻止所有未在准确下一任务的新证据之前执行的空转 poll；超过 60,000ms 等待预算的 poll 也会被独立阻止。时间是由 harness 提供的单调时间证据，而不是模型的声明；不会将纠正对话原文放入提示词。可以通过 `node .\evals\verify-behavioral-interlock.mjs` 运行包含 34 个 case 的确定性门禁。实际的 hook 接口是 `node .\evals\behavioral-interlock.mjs --trace <runtime-trace.json>`；如果不带 trace 直接运行，则以 exit 64 结束，避免在什么都未检查的情况下看起来像是成功。运行时也可以无副作用地 import 同一模块，并在进程内完成判定。这是可复用的 hook，并不声称已经全局安装到所有 Agent 产品中；要实现硬性强制，还需要运行时与编排器集成。

错误的伴随工作证据不会只返回代码，还会同时返回修复指南和契约允许的 `allowedEvidenceKinds`。该指南可减少拼写错误和集成错误，但不会将状态消息、记忆保存或未声明的证据提升为伴随工作。
允许的完整 enum 列表为 `artifact`、`contract-review`、`fixture-design`、`inventory`、`low-load-analysis`、`verification`、`system-evolution-audit`、`system-evolution-contract`。这样，harness 可以在首次 poll 前根据此列表验证 trace，无需通过被拒绝的执行在事后发现准确拼写。

针对长期任务状态中只报告一个目标轴或编造无依据的整体百分比这类失败，提供 `AS-PRG-001` 多轴进度契约和参考 hook。必须将 harness 声明的所有轴分别以`完成数/总数·准确百分比·失败分类·当前阶段·下一验证阶段`进行报告。如果权威分母尚未确定，则不估算百分比，并单独标示当前测量范围以及分母尚未确定的原因。还会阻止将不同分母合并为一个整体百分比，从而掩盖任务轴。通过 `node .\evals\verify-progress-report.mjs` 运行正常、边界和负面对照组共 11 个用例；`progress-report.mjs --trace` 会以 exit 2 终止于缺失的 stdlib 轴、计算错误的比例或估算的分母。

`AS-BI-001`要求在将 Agentic Shaping 或 Slogs LLM Wiki 的审计·契约实现作为安全的伴随工作时，同时提供目标系统和实际资产依据。仅凭进度消息、记忆 capture/write 以及模型的声明，不能更新等待预算。常规 `artifact` 证据也可以选择性地在 `artifactEvidence` 中记录实际资产路径；如果记录，则不允许存在空项或仅包含空白的项。扩展后的确定性门禁共有 34 个，仍保持禁止修改既有输入以及禁止竞争性高负载工作的要求。

对于在高成本门禁前只修复变更不变量的部分 downstream consumer 的失败，仓库提供 `AS-EG-001` 高成本门禁契约和参考 hook。预计耗时60,000ms以上的门禁，只有在每个变更契约都具备与 harness 声明的 consumer 集合精确一致的通过审计、正负 cheap probe，以及 preflight 前后相同的输入 SHA-256 时才能启动。模型编写的证据、consumer 缺失或重复、单边或失败的 probe、输入 drift 和未知字段均 fail closed。运行 `node .\evals\verify-expensive-gate.mjs` 可执行11个确定性案例，并可通过 `--evidence` 将允许 exit 0 与阻止 exit 2 接入编排器。这是参考 hook；硬性强制要求 harness 从权威事件构造 consumer、审计和 probe 证据。

对于错误地把协作目标路由到记忆路径的失败，仓库提供 `AS-CR-001` 协作路由契约和参考 hook。它区分个人/项目记忆、Agentic Shaping 演进和 Slogs LLM Wiki 系统演进。`in-progress` 阶段保留主任务未完成状态，同时要求每个系统具备预先评估契约及审计或实际变更证据；只有 `final` 阶段才要求当前任务完成、真实 prompt/hook 变更和行为验证。运行 `node .\evals\verify-collaboration-routing.mjs` 可执行12个对照案例。

### v0.3 技术备忘录

`AS-SA-001` 会先将重复信号的抽象层级判定为 `local`、`project`、`cross-project` 或 `general-method`。`local` 和 `project` 会阻止共享登记；只有在充分确认适用于不同范围的 `cross-project` 和 `general-method`，才会移除项目标识符与个人引用，并合成为通用技能包。对于个人信息、项目机密、凭据、秘密信息、不安全路径、泛化不足，以及缺少正常、边界和负向评估的情况，检查均会按故障安全方式判定失败。当前抽象化与安全性检查已通过 25/25，并与 Slogs Skills 的 `skill_registry_submit_candidate` 输入及 `validated-candidate` 状态一致。不过，由于尚未部署到生产 Slogs MCP，尚未执行实际候选登记；因此当前状态为 `structured-and-applied`，不会将其表述为已完成生产环境应用或实现效果改善。

`AS-PS-001` 负责重要政策·评估变更的公开同步。在单一权威版本中同时更新政策·评估、4 种语言的主页、4 种语言的 README 和 `CHANGELOG.md`；如果版本·数值·契约·生成结果不一致，会在 push 和部署前失败。文字·兼容性 bug 修复为 `patch`，向后兼容的功能添加为 `minor`，破坏现有公开契约的变更为 `major`。本次技能发现·Slogs 候选关联属于向后兼容的功能添加，因此记录为 `0.2.0 → 0.3.0`。

已确认的最终提示词行为契约也已同步到 Slogs LLM Wiki 的韩语·英语运行时政策中。当前政策版本为 `2026.09.04.2`，并明确执行以下内容。

## 与 LLM Wiki 一起使用

Agentic Shaping 仅凭当前对话和项目指引即可开始使用。但对话结束后，期间发现的上下文可能会消失。

- **与 LLM Wiki 一起使用，效果会更好。** 可以长期保留更正、偏好和判断标准，并在下一项工作开始前再次取用。
- **与 Slogs LLM Wiki 一起使用，效果会再上一个台阶。** 可以同时进行工作前的主动回忆、捕捉意图修正信号、分离全局原则与项目记忆，以及保留依据的更新流程。

重要的不是存储很多内容，而是在工作开始前找到相关记忆，将其实际应用到计划和结果中，并在验证后再次更新的循环。

## 安全边界

Agentic Shaping 不是扩大 Agent 权限的方法。

- 不超出当前用户请求的范围和权限。
- 不将敏感信息、令牌、密码和一次性日志保存为记忆。
- 当前请求与过往记忆冲突时，以当前请求为优先。
- 不混淆通用原则与项目特定的语法·契约·验证标准。
- 不会仅因某件事可以自动化，就把创造性判断也缩减为机器规则。
