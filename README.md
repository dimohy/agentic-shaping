# Agentic Shaping

> AI Agent가 작업 속 암묵지·취향·교정·실패를 먼저 발견하고, 다음 실행에 다시 쓸 수 있는 기억·규칙·도구·검증기로 빚어 사용자의 방식으로 함께 진화하는 작업법입니다.

[공식 실전 가이드](https://agentic-shaping.slogs.dev/) · [dimohy의 배경 이야기](https://slogs.dev/@dimohy/vibe-compiler)

현재 공개 버전: **v0.2**

![사람의 작업 흔적을 Agent가 재사용 가능한 규칙과 자산으로 조직하는 Agentic Shaping 장면](assets/agentic-shaping-hero.jpg)

## 왜 필요한가요?

AI와 함께 일하면 첫 결과는 빠르게 나옵니다. 하지만 다음 작업에서 같은 문체를 다시 설명하고, 전에 싫다고 했던 결과를 다시 고치고, 이미 겪은 실패를 뒤늦게 또 발견한다면 속도는 쌓이지 않습니다.

Agentic Shaping은 좋은 결과 하나에 머물지 않습니다. 작업할 때마다 **다음 결과를 만드는 Agent와 실행 시스템 자체를 조금씩 개선**합니다.

- “이런 문장은 싫어요”라는 교정은 다음 문서의 문체 기준이 됩니다.
- 반복되는 입력 형식은 스키마와 타입이 됩니다.
- 자주 빠뜨리는 검사는 조기 검증기와 회귀 테스트가 됩니다.
- 매번 손으로 하던 순서는 명령·템플릿·파이프라인이 됩니다.
- 검증된 새 경로가 생기면 임시 스크립트와 중복 경로는 정리됩니다.

## 어떻게 작동하나요?

Agentic Shaping은 다음 순환을 반복합니다.

| 단계                   | Agent가 하는 일                                                          | 남아야 하는 결과        |
| ---------------------- | ------------------------------------------------------------------------ | ----------------------- |
| **Detect**             | 반복 설명, 사용자 교정, 싫어한 결과, 늦은 실패와 수동 판단을 감지합니다. | 개선 후보               |
| **Capture**            | 원치 않았던 전개와 원인, 원한 방향, 적용 범위를 포착합니다.              | 근거가 있는 판단 기준   |
| **Structure**          | 판단과 데이터를 기억·루브릭·스키마·타입·fixture로 정형화합니다.          | 재사용 가능한 계약      |
| **Apply**              | 다음 작업 전에 관련 자산을 찾아 계획과 결과에 먼저 적용합니다.           | 달라진 실행 경로        |
| **Verify**             | 실제 파일·화면·런타임·배포 결과로 확인합니다.                            | 재현 가능한 증거        |
| **Simplify / Measure** | 중복과 우회 경로를 없애고 속도·정확도·재현성의 변화를 확인합니다.        | 더 단순하고 강한 시스템 |

핵심 책임은 나뉩니다.

- 의미, 맥락, 모호성, 창의적인 선택은 AI Agent가 담당합니다.
- 반복 형식, 불변식, 실패 조건, 실행 순서처럼 기계적으로 판정할 수 있는 것은 코드와 계약이 담당합니다.

Agent가 모든 것을 기억하게 만드는 것이 아닙니다. **반복되는 비정형 판단을 발견하고, 다시 쓸 가치가 있는 것만 정형 자산으로 승격하는 것**이 핵심입니다.

## 문서와 소스코드가 커지면 분석 방식도 진화합니다

Agentic Shaping이 작동할수록 문서, 바이브 코딩 소스, 설정, 로그, 테스트가
늘어납니다. 이때 Agent가 전체 원문을 매번 다시 읽게 두면 서비스 응답과 컨텍스트
한계 때문에 탐색이 느려지고, 관련 정보가 긴 입력 속에 묻혀 분석이 부정확해질 수
있습니다. 이것도 정형화해야 할 반복 작업입니다.

- 반복 전체 스캔, 긴 도구 출력, 같은 심볼·의존 관계 재탐색을 shaping 신호로 봅니다.
- 기존 검색·파서·컴파일러·테스트로 답할 수 있는 것은 먼저 재사용합니다.
- 부족한 부분만 인벤토리, 문서/심볼 인덱스, 호출·의존·영향 그래프, 범위 질의,
  일관성 검증기로 승격합니다.
- 원문은 계속 권위 있는 진실원입니다. 분석 결과에는 원문 위치와 버전/해시를 남기고,
  변경 시 갱신하며, 오래된 결과는 조용히 사용하지 않습니다.
- Agent에는 저장소 전체가 아니라 현재 과업에 필요한 작은 근거 묶음을 제공하고,
  의미·맥락·모호성은 Agent가 판단합니다.

목표는 요약 문서를 또 쌓는 것이 아니라 **원문에 추적 가능하고 다시 생성할 수 있는
분석 표면**을 만드는 것입니다. 다음 실행에서 전체 재분석량·컨텍스트 사용량·탐색
시간·누락·재시도가 실제로 줄어드는지 측정합니다.

## 무엇이 달라지나요?

| 작업        | 처음에는                            | Agentic Shaping이 쌓인 뒤에는                           |
| ----------- | ----------------------------------- | ------------------------------------------------------- |
| 코딩        | 증상을 고치고 끝냅니다.             | 원인을 타입·불변식·테스트에 반영해 재발을 막습니다.     |
| 문서        | 문체와 구성을 매번 다시 설명합니다. | 승인된 문체·구조·금지 표현을 먼저 적용합니다.           |
| 분석        | 기준이 대화 속에만 남습니다.        | 입력 스키마·판정 기준·재현 가능한 분석 절차로 남습니다. |
| 이미지·영상 | 수정 의견이 다음 제작에 사라집니다. | 스타일 규칙·장면 계획·검수 기준으로 이어집니다.         |
| 배포        | 성공 메시지만 보고 완료합니다.      | 실제 URL·인증서·화면·상태를 확인하는 게이트가 생깁니다. |

그 결과 사용자는 같은 설명과 같은 수정을 덜 반복하고, Agent는 작업을 거듭할수록 사용자의 완료 기준에 더 빨리 도달할 수 있습니다.

## 5분 안에 시작하기

1. 아래 프롬프트를 사용하는 Agent의 지속 지침에 넣습니다.
   - Codex: 전역 또는 프로젝트 `AGENTS.md`
   - Claude Code: `CLAUDE.md`
   - GitHub Copilot: 저장소 지침
   - 그 밖의 Agent: 프로젝트 지침이나 시스템 프롬프트
2. 평소처럼 실제 작업을 요청합니다.
3. 결과가 마음에 들지 않으면 이유와 원하는 방향을 자연스럽게 교정합니다.
4. Agent가 그 교정을 현재 결과에만 반영하지 않고, 다음 실행에 쓸 자산으로 승격했는지 확인합니다.
5. 완료 보고에서 실제 검증 결과와 새로 만든 재사용 자산을 확인합니다.

처음부터 거대한 자동화 시스템을 만들 필요는 없습니다. 반복되는 판단 하나를 체크리스트나 검증기로 옮기는 것부터 시작하면 됩니다.

## 적용 프롬프트

아래 내용을 그대로 복사해 사용할 수 있습니다.

```text
Agentic Shaping v0.2

이 작업에는 Agentic Shaping을 적용해줘.

설명이나 제안만 하지 말고 현재 요청을 끝내는 행동은 항상 수행하며, 재사용 가치가 확인된 신호가 있을 때는 다음 실행을 개선하는 행동도 함께 수행한다. 여러 단계가 필요하면 편한 일부만 고르지 말고 완료에 필요한 전체 경로를 실행한다.

작업을 계획하거나 행동을 선택할 때는 ① 현재 요청의 결과를 실제로 완성하는 행동, ② 민감정보·권한·형식 같은 안전 경계를 지키는 행동, ③ 재사용 가치가 확인된 경우에만 다음 실행을 개선하는 행동을 각각 독립적으로 확인하고, 해당되는 행동을 모두 명시적으로 수행한다. 하나를 수행했다는 이유로 다른 하나가 암묵적으로 끝났다고 간주하지 않는다.

사용자가 명시적으로 일회성이고 재사용할 필요가 없다고 한 정보·상태·작업은 현재 요청만 완료하고 필요한 비밀 제거·안전 처리를 수행한다. Agentic Shaping을 적용한다는 이유로 억지로 기억·전역 규칙·재사용 자산을 만들지 않으며, 저장하지 않는다는 판단이 현재 요청 완료를 대신하지도 않는다.

1. 범위·기억 게이트
   - 시작 전에 관련된 내 과거 결정, 선호, 프로젝트 규칙과 권위 자료를 찾아 실제 계획과 산출물에 반영한다.
   - 현재의 명시적 요청이 과거 기억보다 우선한다.
   - ① 요청된 산출물을 현재 범위 안에서 완료하고, ② 관련 비민감 선호·스타일은 실제 산출물에 적용하며, ③ 제외한 무관한 프로젝트 규칙·다른 계정 권한·자격 증명은 범위 밖이라고 구분한다. 세 항목은 서로 대신할 수 없다.
2. 신호 감지
   - 내가 반복해서 설명한 것, 수정한 것, 싫어한 결과, 성공 조건, 반복 실패, 수동 판단, 비싼 재실행, 근거 없이 성공·최적화됐다는 주장을 별도 지시 없이 포착한다.
3. 현재 해결 + 다음 실행 구조화
   - 신호가 있으면 현재 결과만 고치고 멈추지 않는다. 현재 작업 완료 → 원인·판단 기준 포착 → 권위 자산 갱신 → 조기 검증·회귀 검사 → 실제 결과 확인까지 필요한 전체 경로를 수행한다.
   - 적용 범위에 맞춰 다음 형태로 승격한다.
   - 취향·판단 기준 → 기억, 체크리스트, 루브릭
   - 반복 입력·데이터 → 스키마, 타입, enum, 매니페스트
   - 반복 작업 → 템플릿, 명령, 스크립트, API, 파이프라인
   - 반복 실패 → 불변식, 조기 검증기, 테스트 fixture
   - 반복되는 버전·경로·설정 상수 → 단일 권위 값으로 통합하고 관련된 모든 하드코딩을 교체
4. 컨텍스트 확장 게이트
   - 문서·소스·로그가 커져 전체 읽기와 같은 탐색이 반복되면, 기존 검색·파서·컴파일러·테스트를 먼저 발견하고 검증해 작업 흐름에 통합한다. 부족한 분석만 인벤토리·인덱스·심볼/의존 그래프·범위 질의·검증기로 정형화한다.
   - 원문을 권위로 보존하고 분석 결과를 원문 위치와 버전/해시에 추적 가능하게 한다. stale 결과는 갱신하거나 실패시키며, Agent에는 현재 질문에 필요한 작은 근거 묶음만 제공한다.
5. 판단 경계
   - 의미·모호성·창의성은 Agent가 판단하고 요청된 창작 변형은 실제로 만든다. 재사용 취향은 사용자에게 확인된 것만 포착하며, 확인된 것이 없다는 판단도 명시하고 일회성 선택을 영구 규칙으로 만들지 않는다.
   - 창작 작업에서도 명시된 텍스트 수·가독성·출력 형식·경로를 별도로 검증한다. 그 밖의 불변식·실패 조건처럼 기계 판정 가능한 것은 코드와 계약으로 검증한다.
6. 실행 전·후 검증
   - 고비용·파괴적·배포 작업은 입력 계약, 정확한 대상, 권한, 실패 조건을 먼저 검증한다. 경고와 silent fallback을 성공으로 숨기지 않는다.
   - 실제 파일·화면·런타임·공식 URL·배포 상태로 완료를 확인한다. 검증된 새 경로가 있으면 중복·임시·우회 경로를 정리하고, 개선 효과는 시간·컨텍스트·누락·재시도 변화로 측정한다.
7. 완료 보고
   - 현재 요청의 결과, 적용한 과거 결정, 새로 포착·구조화한 재사용 자산, 실행한 검증, 남은 한계를 구분해 알려준다.

현재 요청과 권한을 넓히지 말고, 민감 정보·일회성 상태·검증되지 않은 추측은 저장하지 마.
```

## 이렇게 요청해 보세요

### 작업을 시작할 때

```text
이 기능을 구현해줘. 시작 전에 관련된 내 결정과 프로젝트 규칙을 먼저 찾아 적용하고,
반복되는 판단이나 실패 조건이 보이면 다음 작업에서 재사용할 수 있는 타입·검증기·테스트로 승격해줘.
```

### 같은 문제가 반복됐을 때

```text
증상만 고치지 말고 왜 미리 발견하지 못했는지 찾아줘.
다음부터는 Agent의 수동 판단보다 타입·스키마·불변식·조기 검증기가 먼저 발견하게 만들어줘.
```

### 작업을 마쳤을 때

```text
방금 작업을 Agentic Shaping 관점에서 돌아봐줘.
이번에 발견한 내 판단 기준, 반복한 수동 작업, 늦게 발견된 실패와 새로 만든 재사용 자산을 구분하고,
다음 실행에서 무엇을 먼저 적용할지 정리해줘.
```

## 좋은 결과인지 확인하는 법

프롬프트에 그럴듯한 문장이 들어 있다고 Agentic Shaping이 작동한 것은 아닙니다. 다음 질문에 실제 증거로 답할 수 있어야 합니다.

- Agent가 사용자의 교정이나 반복 실패를 스스로 발견했나요?
- 다음 작업에 다시 쓸 수 있는 기억·규칙·스키마·테스트·도구가 생겼나요?
- 산출물 규모가 커질 때 전체를 다시 읽지 않고도 필요한 근거를 찾는 정형 분석 표면이 생겼나요?
- 그 분석 결과는 원문 위치·버전/해시에 추적 가능하고 변경 시 갱신되나요?
- 그 자산을 다음 실행 전에 먼저 찾아 실제 계획과 결과에 적용했나요?
- 실제 파일·화면·런타임·배포 상태로 검증했나요?
- 검증된 새 경로가 생긴 뒤 중복·임시·우회 경로를 정리했나요?
- 이전보다 재설명, 수동 판단, 재시도 또는 늦은 실패가 줄었나요?

이 저장소의 `evals/`는 공개 프롬프트를 적용하지 않은 기본군과 적용군에 같은 과제를 주되, 일반 작업 품질과 Agentic Shaping 고유 발동을 분리해 비교합니다.

- Agentic Shaping 차별 평가: 26개 짝 시나리오, GPT-5.6 Luna Max 52회 실행
- 고유 행동 완전 통과: 기본군 16/26(61.5%), 적용군 25/26(96.2%)
- 고유 행동 세부 기준: 기본군 82/105(78.1%), 적용군 104/105(99.0%)
- 처음 보는 최종 holdout: 기본군 3/5(60%), 적용군 5/5(100%)
- 현재 작업 완료: 양쪽 27/27, 금지 행동: 양쪽 0건
- 일반 품질·안전 회귀: 기본군 94/98(95.9%), 적용군 96/98(98.0%), 금지 행동 0건
- 실제 파일 실행 평가: 양쪽 6/6 (한 과제의 회귀 없음만 확인하며 프롬프트 우위를 입증하지 않음)

평가 자체도 Agentic Shaping의 대상입니다. 이번 검증에서는 적은 표본, 기본군 지시 오염, 모호한 사례, 반복 실패, 전체 재실행 비용, timeout을 신호로 포착해 다음 자산으로 승격했습니다.

- 일반 품질 회귀와 Agentic Shaping 차별 점수를 분리
- 개발 세트, 결과를 본 holdout, 처음 보는 최종 holdout을 구분
- 실패 사례 필터로 먼저 재생한 뒤 전체 회귀 실행
- 실패 반복 결과를 버리지 않고 iteration JSON과 관찰 문서로 보존
- suite·프롬프트·모델·사례 목록 해시가 일치할 때만 checkpoint/resume
- timeout을 프롬프트 실패와 분리하고 한 번만 재시도
- `tests/` 아래의 통과 테스트를 놓친 채점기 결함을 보존하고 재귀 탐색으로 교정

확인된 최종 프롬프트 행동 계약은 Slogs LLM Wiki 한국어·영어 런타임 정책에도 동기화했습니다. 최종 정책 버전은 `2026.08.25.3`이며 다음을 명시적으로 실행합니다.

- 현재 결과 완성, 민감정보·권한·형식·범위 보호, durable 신호 기반 다음 실행 개선을 독립 확인
- 명시적 일회성 작업에는 억지 기억·전역 규칙·재사용 자산을 만들지 않음
- durable 신호는 원인·기준 포착, 권위 자산, 조기 검증·회귀, 실제 결과 확인까지 완주
- 반복 버전·경로·설정은 단일 권위로 통합하고 관련 하드코딩을 모두 교체

[Slogs LLM Wiki 최종 한국어 정책](https://slogs.dev/prompts/slogs-mcp.ko.md)과 [버전 endpoint](https://slogs.dev/prompts/slogs-mcp.version)에서 동기화 상태를 확인할 수 있습니다.

문구 포함만 확인하지 않고 라이브 정책 URL을 직접 Luna Max에 주입해 5개 짝 회귀·10회 Agent 실행을 수행했습니다. 고유 행동은 기본군 18/20(90%)에서 정책 적용군 20/20(100%)로 개선됐고 금지 행동은 양쪽 0건이었습니다. 이 사례는 이미 공개된 회귀 세트이며 새로운 미공개 holdout으로 해석하지 않습니다. 원본은 `evals/slogs-policy-smoke-luna-max.json`에 보존됩니다.

이 결과는 GPT-5.6 Luna Max의 고정 세트 단일 실행에서 얻은 기술 통계이지 모집단 추정이나 모든 모델·도구 환경의 보장이 아닙니다. 적용군도 버전 드리프트에서 한 행동을 놓쳤습니다. 프롬프트가 바뀌면 같은 평가와 실제 실행 게이트를 다시 실행해야 합니다.

```powershell
node .\scripts\check-readme-prompt.mjs
node .\scripts\check-eval-report.mjs
node .\scripts\check-slogs-policy-sync.mjs
node .\evals\run-evals.mjs
node .\evals\run-execution-eval.mjs
```

## LLM Wiki와 함께 사용하기

Agentic Shaping은 현재 대화와 프로젝트 지침만으로도 시작할 수 있습니다. 하지만 대화가 끝나면 그동안 발견한 맥락이 사라질 수 있습니다.

- **LLM Wiki와 함께 쓰면 더 잘 작동합니다.** 교정·취향·판단 기준을 오래 남기고 다음 작업 전에 다시 꺼내 쓸 수 있습니다.
- **Slogs LLM Wiki와 함께 쓰면 한 단계 더 잘 작동합니다.** 작업 전 선제 회상, 의도 보정 신호 포착, 전역 원칙과 프로젝트 기억의 분리, 근거를 보존하는 갱신 흐름을 함께 사용할 수 있습니다.

중요한 것은 많이 저장하는 일이 아닙니다. 관련 기억을 작업 전에 찾아 계획과 결과에 실제로 적용하고, 검증한 뒤 다시 갱신하는 순환이 중요합니다.

## 안전 경계

Agentic Shaping은 Agent의 권한을 넓히는 방법이 아닙니다.

- 현재 사용자가 요청한 범위와 권한을 넘지 않습니다.
- 민감 정보, 토큰, 비밀번호, 일회성 로그를 기억으로 남기지 않습니다.
- 현재 요청과 과거 기억이 충돌하면 현재 요청을 우선합니다.
- 일반 원칙과 프로젝트별 문법·계약·검증 기준을 섞지 않습니다.
- 자동화할 수 있다는 이유만으로 창의적 판단까지 기계 규칙으로 축소하지 않습니다.
