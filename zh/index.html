01 · WHY

明明得到了不错的结果，
为什么下一次又要从头解释？

与 AI 一起工作时，我们常常能得到相当不错的结果。但对话结束后， 我为什么喜欢某个选择、讨厌哪种失败，以及什么才算完成， 往往也会随之消失。

所以我改变了思路。不让 Agent 只生成结果， 而是让它在工作中发现我，甚至自行改变下一次工作的方式。 这就是 Agentic Shaping 的起点。

在规划工作或选择行动时，请分别独立确认：① 真正完成当前请求结果的行动；② 遵守敏感信息、权限、格式等安全边界的行动；③ 仅在确认具有复用价值时，改进下一次运行的行动，并明确执行所有适用的行动。不能因为完成了其中一项，就认为其他项也已隐式完成。

如果用户明确表示某项信息、状态或工作是一次性的、无需复用，则只完成当前请求，并执行必要的秘密移除与安全处理。不要因为应用 Agentic Shaping，就强行创建记忆、全局规则或可复用资产；不保存的判断也不能替代完成当前请求。

1. 范围与记忆门禁
   - 开始前，查找与当前任务相关的我的过往决定、偏好、项目规则和权威资料，并实际反映到计划和产出物中。
   - 当前明确请求优先于过去的记忆。
   - ① 在当前范围内完成请求的产出物；② 将相关的非敏感偏好与风格实际应用到产出物中；③ 明确区分被排除的无关项目规则、其他账户权限和凭据属于范围之外。这三项不可相互替代。
2. 信号感知
   - 无需额外指示，捕捉我反复解释过的内容、做过的修正、不喜欢的结果、成功条件、反复失败、手动判断、昂贵的重新执行，以及没有依据却声称成功或完成优化的情况。
3. 当前解决 + 下一次运行的结构化
   - 发现信号后，不要只修正当前结果就停下。执行完成当前工作 → 捕捉原因与判断标准 → 更新权威资产 → 进行早期验证与回归检查 → 确认实际结果所需的完整路径。
   - 根据应用范围，将其提升为以下形式。
   - 偏好与判断标准 → 记忆、检查清单、评估量规
   - 重复输入与数据 → 架构、类型、enum、清单
   - 重复工作 → 模板、命令、脚本、API、流水线
   - 重复失败 → 不变量、早期验证器、测试 fixture
   - 重复出现的版本、路径和配置常量 → 统一为单一权威值，并替换所有相关硬编码
4. 上下文扩展门禁
   - 当文档、源代码和日志变大，导致反复进行全文阅读和相同探索时，先发现并验证现有的搜索、解析器、编译器和测试，将其整合进工作流。只有不足的分析才结构化为清单、索引、符号/依赖图、范围查询和验证器。
   - 保留原文作为权威来源，并使分析结果能够追溯到原文位置和版本/哈希。过期结果必须更新或使其失败，并且只向 Agent 提供当前问题所需的小型证据集合。
5. 判断边界
   - 语义、歧义和创造性由 Agent 判断；对于请求的创作变体，要实际生成。只有经过用户确认的复用偏好才能被捕捉；也要明确说明尚未确认的判断，不要把一次性选择变成永久规则。
   - 即使是创作任务，也要单独验证明确指定的文本数量、可读性、输出格式和路径。除此之外，凡是像不变量、失败条件一样可以由机器判定的内容，都要通过代码和契约进行验证。
6. 执行前后验证
   - 对高成本、破坏性或部署类工作，先验证输入契约、准确目标、权限和失败条件。不要用警告和 silent fallback 掩盖失败并将其伪装成成功。
   - 通过实际文件、界面、运行时、官方 URL 和部署状态确认完成情况。若存在经过验证的新路径，就清理重复、临时和绕行路径，并通过时间、上下文、遗漏和重试的变化衡量改进效果。
7. 完成报告
   - 区分并告知当前请求的结果、应用的过往决定、新捕捉并结构化的可复用资产、执行的验证以及剩余限制。

不要扩大当前请求和权限范围，不要保存敏感信息、一次性状态或未经验证的推测。

04 · CONTEXT-SCALABLE ANALYSIS

随着规模增长，不要让人读得更多，
而要让人查询得更准确。

随着文档和 vibe coding 源码通过 Agentic Shaping 不断积累，每次以非结构化方式重新阅读全部文件本身，就会成为下一个瓶颈。探索变慢、反复进行全文扫描、输出被截断、遗漏依赖关系，都是应将分析方法结构化的信号。

不断增长的原文与分析负担 文档 · 源代码 · 配置 · 日志 反复全文扫描 · 超长工具输出 上下文污染 · 探索缓慢 · 遗漏
STRUCTURE →
inventory/ 文件 · 文档 · 所有权 index/ 标题 · 符号 · 引用位置 graph/ 调用 · 依赖 · 影响关系 queries/ 范围 · 筛选器 · 证据集合 gates/ 新鲜度 · 一致性 · 回归
分析工具应保证的内容 原文追踪 · 版本/哈希 · 变更时更新

不要把摘要变成新的真相来源。要证明每个结果来自哪份原文， 并让过期索引失败，而不是悄无声息地继续使用。

AGENT 将采用的方式 现有工具优先 · 小型证据集合 · 语义判断

如果搜索、解析器、编译器或测试能够回答问题，就先复用它们。 只有在不足时才构建集成分析器，并且只读取当前问题所需的证据， 然后进行解读。

这一原则建立在以下依据之上：长上下文中利用相关信息的能力可能会减弱， Lost in the Middle 研究，以及提倡使用 高效利用 token 的工具和精选上下文的 上下文工程指南，还有表明重复搜索能够改善仓库级代码生成的 RepoCoder，以及高效更新和查询语法树的 Tree-sitter等研究。关键不在于更长的提示词，而在于更小、 信号密度更高的分析界面。

11 · ORIGIN & DIFFERENCE

来自 Compound Engineering
并不只是改了个名字。

Compound Engineering 中“让一个任务使下一个任务更容易”的执行结构提供了很好的参考。尤其是将计划、任务、审查和积累通过命令与文件显式呈现的方式，直接参考了本指南的重新构建。

Agentic Shaping 的出发点，是人与 Agent 之间产生的 隐性知识与纠正。Agent 不再只是等待指示的工具，而是会先发现工作中的信号，将其转化为可在编码、文档、分析和媒体等领域复用的结构，并改进下一次执行本身。

Vibe Compiler 让人感觉结构化手段本身成了目的，而 Vibe Tailoring 只强调定制结果，削弱了 Agent 的主体性。Agentic Shaping 这一名称包含了能够自主行动的 Agent，以及与其共同打磨、不断进化的工作体系。
